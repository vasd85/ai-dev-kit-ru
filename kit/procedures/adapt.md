# Применить комплект к разрешённому проекту

<a id="permission"></a>
## Разрешение и исходное состояние

Эту процедуру выполняет агент по поручению пользователя. Пользователь описывает
потребность и выбирает существенные продуктовые решения, архитектуру и расходы.
Файлы копирует, профиль заполняет, обычные проверки и исправления выполняет агент.
Подключение не разрешает реализовать весь будущий продукт или опубликовать его.
Сначала установи выданные путь поставки, разрешённый корень продукта, рабочую папку и объём подготовки. До существенной подготовки открой [план и делегирование](roles.md#delegation-and-plan). Перед изменениями установи [полномочия](roles.md#authority) и [владельца ресурсов](roles.md#shared-resources). Для штатной [диагностики](../formats.md#diagnostics) нужны локальные Git и Python 3.

Прочитай правила разрешённого проекта, найди его Git-корень и выбранную рабочую
папку. У нового проекта сначала сохрани идею, разрешённую подготовку и неизвестное;
создавай локальную Git-историю только в разрешённой папке. Для существующего найди
архитектурные документы, правила разработки, реальные задачи Todo/Doing/Done,
их владельцев, приёмки и проверки. Пустой новый `state.json` их не заменяет.
Не запускай неизвестные команды, установку, хуки или генераторы ради осмотра.

<a id="git-inspection"></a>
## Безопасный первоначальный осмотр Git

Прочитай Git-правила проекта. `status` и рабочий `diff` могут вызвать
`filter.<имя>.clean` или `filter.<имя>.process`. Параметры `--no-ext-diff`,
`--no-textconv` и `core.fsmonitor=false` подавляют другие механизмы и не защищают
от этих преобразователей. Поэтому первоначальный осмотр идёт в следующем порядке.
Это маршрут для доверенной локальной среды без конкурентной подмены файлов,
не песочница для произвольного враждебного окружения.

**А. Установить источники, не вызывая обработчики.** Чтением файлов найди корень,
реальный каталог Git (учти gitfile/common-dir) и выбранную папку. Не перенаправляй
команды на другой репозиторий переменными окружения. Установи применимые
`GIT_CONFIG_*`, `GIT_ATTR_*`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`,
объектные перенаправления и параметры запуска; не раскрывай секреты в журнале.
Ниже команды из установленного корня с его настоящим окружением. Неизвестное
перенаправление сначала разбери. Для диагностики `check` сохраняются её более
узкие ограничения из README; способность вручную прочитать источник их не снимает.
Если ограничиваешь `ls-files`, `ls-tree` или `diff` согласованными путями,
ставь глобальный параметр `git --literal-pathspecs` перед подкомандой. После
`--` передавай каждое имя обычного файла отдельным аргументом. В оболочке
заключай буквальный путь в кавычки, а переменную пути пиши как `"$file_path"`.
Кавычки защищают от развёртывания в оболочке. Параметр Git отключает разбор
шаблонов внутри Git, поэтому `draft[1].md` задаёт именно этот файл.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never config --includes --show-origin --show-scope --list
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never ls-files --stage -z
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never ls-files --cached --others --exclude-standard -z
```

`config` здесь только читает значения и подключаемые файлы, не выполняет записанные
команды. Учитывай system/global/local, при наличии worktree, `include/includeIf`
и окружение/параметры команды. Происхождение и порядок значений важны: не выбирай
первое совпадение. Прочитай применимые подключения, включая условия; отсутствующий
или недоступный источник не объявляй пустым по одному успешному коду команды.
`ls-files --stage` даёт режим, ID объекта и стадию каждой индексной записи без
освежения рабочих файлов. Второй список добавляет неигнорируемые новые пути.
Игнорируемое, значимое внешнее и будущие пути подключения добавь явно по файловому
осмотру; список Git не является полным обходом всех данных.

Для каждого затронутого пути задай `file_path` от корня. Прочитай эффективные
атрибуты и их индексный вариант.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never check-attr -z filter diff text eol working-tree-encoding ident -- "$file_path"
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never check-attr --cached -z filter diff text eol working-tree-encoding ident -- "$file_path"
```

`check-attr` сообщает значения, не выполняет clean/process/textconv. Имя фильтра
может быть любым и может прийти через макрос. Проверь `.gitattributes` в папке
файла и предках до корня, индексный fallback при отсутствии рабочего файла,
`$GIT_DIR/info/attributes`, `core.attributesFile` (либо стандартный пользовательский
файл `$XDG_CONFIG_HOME/git/attributes`, по умолчанию `$HOME/.config/git/attributes`)
и системный файл установки Git. `info/attributes` имеет высший приоритет;
более близкий `.gitattributes` перекрывает дальний, пользовательский/системный —
ниже. `check-attr` учитывает доступные применимые источники; его вывод не доказывает
доступность каждого из них. Установи пути/доступность, прочитай относящиеся правила
и сообщения об ошибках; недоступное или неустановленное сохрани как неизвестное.
Отключённый окружением источник не выдавай за проверенный в обычном окружении.

**Б. Собрать доступные версии без преобразования.** До разбора фильтров допустимы
перечисление/чтение обычных файлов и режимов, названные выше команды, а также
чтение локальных объектов ниже. Сохрани раздельно рабочие байты, индексные
режимы/объекты/стадии, HEAD и признаки незавершённых merge/rebase/cherry-pick в
служебной папке. Не используй для этого `status`, рабочий diff, `hash-object --path`,
`cat-file --filters/--textconv`, refresh/update-index, add или проектные команды.
Не заходи командами Git в подмодули; неизвестное в них фиксируется отдельно.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 GIT_NO_REPLACE_OBJECTS=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never ls-tree -rz --full-tree HEAD
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 GIT_NO_REPLACE_OBJECTS=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never cat-file blob "$object_id"
```

`object_id` агент задаёт точным ID blob из индекса или дерева коммита, не путём с
догадкой о стадии. Сравни индекс с HEAD по ID/режимам; содержимое каждого blob —
отдельно с рабочими байтами. Это байты сохранённого объекта без фильтра, не результат
clean рабочего файла. Даже равенство байтов не доказывает Git-эквивалентность при
неизвестном преобразовании (включая text/eol/encoding). Отсутствующий HEAD нового
проекта допустим и так записывается. Отсутствующий/внешний объект, ошибка чтения
или неподдерживаемое устройство Git остаются неизвестными; сеть/получение объектов
не запускаются. Временные `GIT_NO_LAZY_FETCH=1` и `protocol.allow=never`
запрещают получение по протоколам; `GIT_NO_REPLACE_OBJECTS=1` в командах объектов
показывает исходные объекты без refs/replace, а не их обычное замещённое представление. Эти команды не обещают поддержку partial clone/worktree программой
`check` и не устанавливают полностью обычный Git-status.

**В. Разобрать и продолжить.** По эффективному `filter` найди все применимые
`filter.<имя>.clean`, `.process`, `.required` и при записи `.smudge`; process имеет
приоритет над clean. Прочитай команду и доступный код/условия/внешние зависимости,
не запускай неизвестное для выяснения поведения. Аналогично установи diff.external,
драйверы diff/textconv, fsmonitor, а перед записью hooks и signing. Неизвестный,
обязательный или неподдерживаемый обработчик сохраняет ограничение затронутой
операции, а не запрещает все проекты с фильтрами. Дальше можно читать доступные
версии и подготовить разрешённые файлы подключения с точной областью правок.
Следующий шаг — разобрать конкретный источник/обработчик; коммит можно отложить
с причиной. Существенное недостающее разрешение решается по правилам проекта,
обычные технические детали агент выясняет сам.

Когда для всей области команды установлено отсутствие преобразователя либо
конкретный преобразователь изучен и его исполнение допустимо в выданных полномочиях,
можно выполнить обычный осмотр ниже. Наличие безвредного имени или одного
изученного фильтра не разрешает другие. Не запускай корневой status, если разобрана
только часть путей; при неизвестном оставайся на маршруте А–Б.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never status --short --ignore-submodules=all
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never diff --no-ext-diff --no-textconv --ignore-submodules=all
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never diff --no-ext-diff --no-textconv --ignore-submodules=all --cached
```

Подмодули здесь исключены, их состояние не объявляется проверенным. Подавление
внешнего diff/textconv/fsmonitor действует только для этих вызовов и не отключает
clean/process. Не вноси постоянных отключений фильтров, hooks или signing и не
обходи обязательные проверки настоящей записи. Читающий маршрут сам не разрешает
исполнение проектного кода. Перед add/commit повторно проверь относящиеся условия:
изменяющая команда может освежать и другие записи индекса даже при точных путях.

Установи владельца изменяющих операций и судьбу прежних исполнителей: отсутствие
сообщения не доказывает остановку. Чужие правки/индекс не откатывай и не включай в
свой коммит. При чужом незавершённом merge/rebase/cherry-pick коммит подключения
отложи. Сохрани исходные байты/режимы изменяемых файлов и понятную исходную точку
Git. Не создавай коммит всей папки по умолчанию. Перед записью открой [конкретный Git-процесс](#external-delivery), а при чужом индексе — [порядок сохранения](#shared-index).

Основания — в [справке об осмотре Git](../reference/decisions.md#git-history).

<a id="effective-entry"></a>
## Найти фактически читаемый вход

Для каждой разрешённой рабочей папки запиши цепочку от корня проекта до неё.
В каждой папке Codex выбирает максимум один непустой файл: `AGENTS.override.md`,
затем `AGENTS.md`, затем настроенные резервные имена. Вложенные правила имеют
более высокий приоритет. Глобальные инструкции тоже действуют; их не меняют.
Без найденного корня документация описывает проверку только текущей папки.
Не угадывай недоступную конфигурацию/границу корня; зафиксируй неизвестное.

Цепочка собирается при старте и имеет настраиваемый предел объёма. Проверь доступные местные настройки и возможное усечение. Блок должен предписывать явно прочитать файлы. При проверке отдельно запиши, какие файлы доступны, что явно прочитано в текущем чате и наблюдался ли новый старт. [Основание порядка загрузки](../reference/decisions.md#entry-history).

Если в одной папке существуют оба файла, блок только в обычном `AGENTS.md`
недостижим без перехода из выбранного override. Достаточны три варианта:

1. Добавить короткий блок в действующий файл, сохранив прежние правила.
2. Переиспользовать или добавить явный переход из него к обычному файлу с блоком.
   Например: «Явно прочитай раздел ai-kit в корневом AGENTS.md; прежние правила
   этого override имеют приоритет в своей области». Не загружай весь обычный файл,
   если это возвращает намеренно отменённые им правила. Сохрани область исключений.
3. Если действующий вход менять запрещено, подготовить явный текст начала чата
   из [образца старта](#request-examples). В недействующем файле ссылку ради вида не добавляй. Автоматическое
   подключение следующей сессии не заявляй.

Проверь более глубокие переопределения. Корневой блок не доказывает пригодность
для любой вложенной папки. Относительные пути блока ниже означают пути от Git-
корня. Документируй этот корень и разрешённые рабочие папки; не меняй смысл путей
при запуске из `services/api`. Текущая сессия после применения явно перечитывает
новый блок, карту, профиль и применимый срез беклога, не ожидая перезагрузки инструкций.

## Выбрать размещение

При копировании рабочей части штатно правила лежат в `.ai-kit/`, память — в
`docs/ai-work/`. Для полного Git-клона из [README](../README.md) используй `.ai-dev-kit/kit/`
непосредственно, без второй копии рабочей части. При конфликте
сравни содержимое, происхождение и принадлежность. Чужую `.ai-kit/`, профиль,
очередь или блок не перезаписывай. Достаточно свободных мест, например
`support/agent-kit/` и `planning/assistant/`. Согласуй все указатели и команды.
Файловые пути JSON всегда относительно Git-корня; ссылки между Markdown-
файлами обычно относительно содержащего их файла, если явно не указано иное.

Рабочая часть 0.3.0 — эти 30 файлов, с сохранением структуры:

```text

```

При копировании переноси эти файлы из полученной поставки; при Git-подключении
они уже находятся в клоне. Запускай `tools/kit.py` непосредственно. Сохрани
модули рядом с ним и файлы страницы в `tools/overview_page/`.
Полная поставка включает также `tests/test_*.py` и три материала `examples/`.
Тесты изготовления и `examples/` остаются в исходной поставке,
в том числе внутри полного клона; их код/учебные задачи не становятся частью
реализации или поручениями продукта.
Для проверки изготовления полной поставки открой [команды](#full-kit-check).

**Git-клон внутри проекта.** Установи два разных корня: корень продукта и
`.ai-dev-kit/` — корень поставки. Все команды/пути состояния продукта относятся
к первому; в частности `check --root` получает корень продукта. Вход и команды
настрой на `.ai-dev-kit/kit/`, формы памяти заполни вне клона. При подключении
сохрани правила продукта и добавь `/.ai-dev-kit/` в его `.gitignore`, если такого
исключения ещё нет. Сначала убедись, что путь не занят чужими данными и не
отслеживается продуктом; существующий tracked-каталог или подмодуль нельзя
молча удалять из индекса. Не добавляй вложенный репозиторий как случайный
подмодуль и не удаляй его `.git`. При другом размещении измени все пути и исключение.

Запиши в профиле URL источника, точный коммит клона, `VERSION`, местные отклонения
и проверенную команду. Диагностика входов продукта не подтверждает игнорируемый
клон: агент отдельно сверяет его коммит и местные правки. Не обновляй его во время
активного исполнения. При работе над самим комплектом его проверяемые исходники
должны быть в отдельном задании и Git-корне поставки. Перед правкой правил продукта открой [местную процедуру](project-rules.md#maintain-rules). Повтор и обновление выполняй по [порядку перехода](#update-and-rollback).

<a id="project-profile"></a>
## Заполнить профиль и выбрать источник работ

Существующие архитектура и `CONTRIBUTING.md` сохраняют нормативный смысл;
профиль ссылается на них, не создаёт вторую редактируемую норму.
Выбери подходящий режим после содержательного сопоставления:

| Режим | Что сохранить и что установить |
| --- | --- |
| Новый проект | Выбрать карточки и создать первую точку продолжения |
| Существующий штатный файл состояния | Сохранить пути и данные, проверить фактический формат. Для действующего файла доступен `check --profile` с его обычным адресом |
| Нужны дополнения процесса | Предложить минимальное недостающее условие в действующем источнике; существенную смену обязанностей согласовать |
| Частичное применение | Сохранить старый единственный беклог; перечислить ручные проверки агента, место их результатов и запреты; существенный компромисс выбирает пользователь |
| Выбран перенос или адаптер | До переключения подготовить соответствие и возврат; отдельно оценить новый программный адаптер, он не появляется от переименования статусов |

Если обязательное условие обеспечить нельзя, соответствующее действие остаётся
заблокированным. Частичный режим не обходит ошибку полной диагностики. Для существующего источника открой [его разбор и перенос](#partial-and-migration) до выбора режима.

<a id="new-project-cards"></a>
### Новый проект от идеи

Скопируй [форму профиля](../templates/project.md) в выбранную память.
Сохрани в ней один указатель `ai-kit:task-source` с форматом `0.3.0`
и фактическим каталогом от корня. Согласуй первый полезный шаг с правом
его подготовить. Создай в каталоге `scope.md` по [форме области](../templates/scope.md),
общую запись выдач с пустым списком, если выдач ещё нет, и первую карточку
в `open/`. Достаточны номер, формат, название и цель. Если шаг ждёт
решения пользователя, запиши конкретный остаток и следующий шаг в `waiting`.
Укажи номер карточки как продолжение общей области. Подробное поручение
появляется, когда ясны достаточность и полномочия.

Запиши в профиль рабочие команды `check`, `tasks` и `overview` с `--profile`,
сохрани корень и проверь первый список и карточку в браузере.
Для небольшого поручения открой [короткий путь по карточкам](workflow.md#card-workflow)
и [форму карточки](../templates/task.json). Чистая [форма состояния](../templates/state.json)
предназначена для прежнего режима файла состояния.

<a id="install-check"></a>
## Подключить и проверить

После выбора источников адаптируй [фрагмент входа](../entry/AGENTS.fragment.md) или явный старт. Подставь корень, размещение комплекта, профиль и при необходимости маркер `product`. Сохрани местные правила и переходы. В частичном режиме профиль называет реальный беклог и точку продолжения.

В профиле сохрани версию из [VERSION](../VERSION), формат, фактическую цепочку и рабочие папки, места файлов, принадлежащие подключению блоки, прежний текст или Git-основание, источник поставки и исходные хеши. Подставь в скопированном профиле и его ссылках фактические пути от корня продукта. Установи [возможности исполнения](roles.md#delegation-and-plan) и заполни соответствующий раздел. Укажи [местные нормы](project-rules.md#apply-project-rules) по области и действию. Реальные команды запиши с рабочей папкой, условиями, результатом и ограничениями. Неизвестную команду обозначь до допустимой проверки.

Явно перечитай действующий вход или старт, карту, профиль, выбранный источник работ и точку продолжения. Проследи маршрут следующего допустимого действия. Сравни разрешённый набор правок и сохранность исходных правил и данных. В штатном режиме выполни [диагностику](../formats.md#diagnostics), в частичном — [проверки агента](#partial-and-migration). Для карточек открой [обзор](../README.md#task-overview) из установленного комплекта. Сопоставь источник штатной команды, список и следующий шаг в браузере. Для существующих назначений и приёмок используй адресный `check --action`.

При изготовлении, проверке подключения/обновления или конкретном новом сомнении
подтверди читающее поведение: до/после проверяемого вызова сравни исходники,
память, рабочие данные, индекс/HEAD и служебные файлы Git. То же требуется при
испытании нового [первоначального осмотра](#git-inspection). Копирование и адаптация намеренно
меняют папку: отдельно проверь точный разрешённый набор правок и сохранность
остального. В штатной работе неизменённым проверенным инструментом выполняй
обычный `check` на предусмотренных переходах; полные снимки всей папки/Git-истории
перед каждым назначением/приёмкой без нового основания не нужны. До сообщения открой [правило отчёта](workflow.md#reporting). Укажи, что подключено, что можно продолжать и какие ограничения действуют.

<a id="full-kit-check"></a>
### Проверка полной поставки

Из папки, содержащей полную `kit/`, выполни:

```sh
GIT_OPTIONAL_LOCKS=0 python3 -B -m unittest discover -s kit/tests -v
```

Команды генераторов и учебные данные находятся в `examples/walkthrough.md` полной поставки. Для генераторов выбирай новые собственные учебные каталоги. Результаты не являются задачами продукта.

<a id="request-examples"></a>
### Образцы запросов

> Примени комплект из `/путь/к/kit/README.md` к разрешённому проекту `/путь/к/проекту`, рабочая папка — его корень. Открой маршрут подключения и проверь допустимое продолжение.

При запрете менять действующий вход передай заполненный [фрагмент входа](../entry/AGENTS.fragment.md) явным сообщением. Например:

> Работай в `/канонический/корень/проекта`, рабочая папка — `services/api`. Соблюдай действующие инструкции [точная цепочка]. Явно прочитай `planning/assistant/project.md`, раздел «Подключение и единственные источники», и `support/agent-kit/README.md#entry-routes`. Пути от корня продукта. Выбери маршрут по действию. Продолжение — [точный раздел или запись].

Этот переход действует при явной передаче сообщения.

<a id="partial-and-migration"></a>
## Существующий беклог и перенос

До выбора режима пройди реальные намеченные, активные и завершённые записи.
Сохрани в профиле путь, прочитанную редакцию, смысл статусов, редакторов,
принимающего и фактические свидетельства. Например, в `Todo → Doing → Done`
последнее может означать только окончание кода. Тогда Done остаётся историческим
утверждением автора, а не принятой проверкой. Дополнение той же карточки полями
«проверка / принимающий / ограничения / следующий шаг» достаточно, если это
согласованный порядок. Не навязывай новый статус или человека-ревьюера.

При частичном режиме старый беклог остаётся единственным источником работ.
Профиль хранит собственный разбор агента: какие ID проверены, зависимости,
действующие владельцы и запись, приёмка/свидетельства, неизвестное, итог/запреты,
следующий допустимый шаг. Это результат проверки названной редакции, а не вторая
редактируемая очередь. При изменении карточки результат устаревает и пересматривается.
Не запускай `check` на пустом штатном состоянии и не называй это проверкой беклога.
Программа может проверить отдельную совместимую область, только если её смысл и
границы явно заданы; полный чужой формат она от этого читать не начинает.
Отсутствующая обязательная приёмка запрещает зависимое назначение. Неизвестный
писатель удерживает запись. Чтение/анализ может продолжаться независимо.

### Подготовка карточек на отдельной копии

1. Из обычной рабочей папки установи [действующий вход](#effective-entry) и
   профиль. Открой фактически выбранный список и штатную команду. Укажи,
   проверяет ли она общий и местный учёт, одну работу либо только форму
   чужого списка. Выполни известную читающую команду в её рабочей папке.
   Код `2` для остановленной попытки формата `0.1.0` или `0.1-p1` сохрани
   вместе с доступными сведениями о процессе. При неизвестной версии
   установи исходную редакцию и совместимый читатель.
2. По [правилам Git](#git-inspection) отдельно прочти рабочие файлы, индекс
   и последний коммит. Скопируй проект в отдельный Git-корень вместе с
   историей, индексом, скрытыми и значимыми игнорируемыми файлами. Определи
   владельцев общего ресурса и исходы активных попыток. Работай с файлами
   кандидата в выделенной свободной папке копии. Действующий профиль
   исходной установки продолжает выбирать прежний список.
3. Заполни [редакторское сопоставление](../formats.md#task-migration). Дай
   каждой работе полный номер области, объясни прежний статус и укажи
   принимающего, доказательство, обязательный остаток и следующий шаг.
   Исторический материал укажи по старому полному коммиту, тогдашнему пути
   и ключу записи, где он нужен. Отметь отдельно дату наблюдения, реального
   решения и время снимка. По профилю и ссылкам на решения найди действующий
   файл, в котором принимающий сейчас уточняет или отзывает решение. Укажи
   его отдельно от исторического адреса в `accept.current_decision` для
   сторонней приёмки. Для свидетельства только в истории сохрани полный
   коммит и прежний путь. Перечисли существенные ссылки и материалы.
   Если есть только отметка `Done` и правка файла, оставь карточку открытой
   с недостающим критерием. Связь потребителя с этой работой подтверди
   проектным правилом либо сохрани вопрос к владельцу.
   Для стороннего источника выпиши независимый перечень номеров из самого
   списка. Сверь его с номерами в сопоставлении и на шаге 6.
4. Выполни инвентаризацию из корня прежней установки новым комплектом.
   Путь `migration_review` указывает на заполненный JSON редактора, а
   `migration_snapshot` на файл результата вне обоих Git-корней.

   ```sh
   python3 -B "$migration_kit/tools/kit.py" migration inventory --root . \
     --review "$migration_review" > "$migration_snapshot"
   ```

5. Из корня выделенной копии выполни подготовку и сверку. Здесь
   `migration_kit` указывает на рабочую часть нового кита на копии, а
   `migration_origin` на отдельный корень прежней установки.

   ```sh
   python3 -B "$migration_kit/tools/kit.py" migration prepare --root . \
     --origin "$migration_origin" --target preview \
     --review "$migration_review" --snapshot "$migration_snapshot"
   python3 -B "$migration_kit/tools/kit.py" check --root . --profile preview/profile.md
   python3 -B "$migration_kit/tools/kit.py" migration verify --root . \
     --origin "$migration_origin" --target preview \
     --review "$migration_review" --snapshot "$migration_snapshot"
   ```

   Для перенесённых приёмок и предложенных назначений приложи к
   `prepare` и `verify` файл `--bindings` со [снимками карточек](../formats.md#migration-bindings).
   Их сохраняет владелец Git на копии. Для следующей редакции адресов
   передай прежний файл через `--previous-bindings` при подготовке.
   Частично сохранённая сборка ждёт повторного вызова с теми же адресами.
   Повтор на совпадающем кандидате сообщает `identical`.
6. Открой карточки обычной командой `tasks` с профилем проверки на копии.
   Историю и текущие материалы открой через `read`. Сверь область, число,
   редакции поручений, байты, связи, доступное следующее действие и границы
   местного мандата. Открой выбранное подтверждение зависимости по его
   точному результату и ключу проверки. Сопоставь его существенные входы
   и пройди обычный `check --action`. Проверь известные внешние исходы
   и расходы по их старым основаниям. Готовность к переключению подтверждают
   `verify: ready` и сверка полного перечня работ.
   Незавершённая проверка расчёта удерживает отчёт, которому нужны числа.
   Неизвестный владелец общего индекса или конфликт стадий в папке
   кандидата удерживает весь переход. Владелец Git разбирает путь и
   отмечает решение в индексе, затем повторяет сверку. При `stale`
   установи изменившийся путь и слой, перечитай основание и подготовь свежую
   копию. Снова открой исходный профиль и выполни прежнюю штатную команду.

Передай снимок, таблицу, исключения и проверенный кандидат координатору.
Переключение требует отдельного поручения и свежей сверки в безопасной точке.

<a id="switch-to-task-cards"></a>
### Прямое переключение на карточки

1. Установи действующий вход и профиль из рабочей папки. Подготовь маршруты
   проверки и чтения карточек в этом профиле заранее. Для совместимого старого
   файла заполни `ai-kit:task-source` его фактическим форматом и путём. Для
   стороннего списка сохранить выбор до переключения помогает явный старый
   путь и команда в профиле. Если прежний профиль был обязательным файлом
   поручений или записями состояния, оставь его точные байты и создай отдельный
   профиль выбора. Переведи действующий вход на него при ещё выбранном старом
   списке. Сними инвентаризацию после этой настройки. Отдельно назови в
   профиле явную команду чтения прежних данных и исторические ссылки.
2. В целевой установке подготовь проверенную папку и её Git-снимки по
   предыдущему разделу. Используй для неё устойчивый путь. Сверка сравнит
   текущую установку с отдельным исходным корнем. При переносе с пробной
   копии переноси подтверждённую папку и адресуемую историю назначенным
   владельцем Git. Сохраняй индекс и прежние входы целевой установки.
   Штатные команды в профиле должны следовать выбранной строке. Открывай
   `tasks` и браузерный обзор при выборе карточек, а старую команду используй
   для старого формата или явного исторического чтения.
3. Общий координатор с редакторами областей приостанавливает выдачу
   затронутых поручений. Установи владельцев, состояние попыток и внешних
   действий, свободные и удерживаемые резервы, владельцев и судьбу
   подготовленных правок Git. Согласуй отсутствие параллельной записи
   до смены источника. Сохрани выводы и основание в JSON записи паузы вне
   папки кандидата. Профиль указывает этот путь в тексте, а для старого
   штатного файла может включить его в поле `pause` указателя до снимка.
   Запись содержит `state: "paused"`, `profile`, `target`, `actor` с сессией
   общего редактора, текстовые `owners`, `attempts`, `external`, `reserves`,
   `index` и `next_step`. Последнее поле описывает безопасное действие
   после смены ссылки. Фактическое прекращение записи подтверждают владельцы.
4. Из корня установки, которую переключаешь, выполни штатную команду.

   ```sh
   python3 -B "$migration_kit/tools/kit.py" migration switch --root . \
     --origin "$migration_origin" --target preview \
     --review "$migration_review" --snapshot "$migration_snapshot" \
     --bindings "$migration_bindings" --actor "$migration_actor" \
     --pause ops/task-transition.json
   ```

   Для кандидата без сохранённых решений или действий опусти `--bindings`,
   если в подготовке он не использовался. При успехе программа ещё раз сверяет
   рабочие байты, индекс, историю и кандидата. Затем атомарно заменяет только
   строку выбора в действующем профиле или добавляет её при старом стороннем
   списке. Она не сохраняет файл в Git. При `stale` продолжает действовать
   прежний список. Владелец устанавливает изменившийся путь и причину,
   фиксирует `state: "stopped"` с допустимым прежним продолжением и повторяет
   подготовку на свежей основе. Чужие правки остаются их владельцам.
5. При остановке до смены ссылки снова прочитай прежний список и запись паузы.
   При остановке после неё штатный `check --profile` читает карточки и
   показывает паузу. Координатор сохраняет только изменённый профиль в Git
   по [порядку сохранения путей](#shared-index), с отдельной сверкой чужого
   индекса, и повторно проверяет каждый затронутый переход по фактическому
   профилю. Повтор `switch` от действующей сессии общего редактора при
   выбранных карточках показывает источник, состояние выдачи и допустимый шаг.
   Если запись направляет к прежнему списку при выбранных карточках,
   обе команды называют расхождение. Общий координатор сверяет запись
   перехода с профилем перед продолжением.
6. Для каждой перенесённой приёмки проверь `handoff`, для зависимого
   назначения — `assign` с его попыткой и редактором. Сверь местный мандат,
   действие, точный результат и ключ выбранной проверки, а также актуальные
   рабочие, индексные и сохранённые входы. Изменившийся вход разбирает владелец
   соответствующего решения по [пересмотру](recovery.md#reassess).
   Сохрани подтверждённые действия, ожидания, их владельцев и следствия для
   выдачи в `evidence` записи паузы. При общей готовности действующий
   координатор меняет её на `state: "reviewed"`, указывает свою сессию
   в `actor` и записывает допустимый шаг. Сессию и роль обе команды
   берут из общего `scope.md`. При [передаче роли](recovery.md#card-resume)
   новая сессия общего редактора сверяет основания и подтверждает решение
   о выдаче от своего имени. Адресная проверка поручения и его оснований
   доступна во время корректной паузы. Выдача и запуск ждут решения общего
   координатора и подходящего итога адресной проверки. Сверь обычный вход
   преемника, штатную команду и браузер с фактическим профилем.

<a id="external-delivery"></a>
## Git-процесс и внешняя доставка

Перед действием на внешнем сервере, публикацией или выпуском установи явное разрешение, владельца, доступ, требуемые проверки, точную версию и возврат. Найди прежние попытки по операции, цели и ресурсу в общих и связанных записях, в том числе у работы с другим ID. При неизвестности сначала пройди [выяснение исхода](recovery.md#uncertain-outcome). Приёмка задачи и право на локальные Git-операции сами по себе не разрешают доставку.

Если правила уже в `CONTRIBUTING.md` или другом нормативном файле, профиль
ссылается на него и фиксирует проверенные команды. Изменение правила делается
в его источнике. Выбор сервера/публичности сам не разрешает передачу данных.
Ниже условные примеры, а не настройки каждого продукта.

**Локальный проект одного автора.** Условия: только локальная история, один
агент пишет, пользователь выбрал результат и разрешил местную реализацию.
`main` достаточна; для рискованной работы — временная ветка. Агент сохраняет
входы и поручение до проверки, затем результат/приёмку отдельным коммитом.
Перед объединением сравниваются итоговые входы, выполняются необходимые тесты;
тот же текст входов после merge не требует повторять все тесты без основания.
Приёмка поведения и общий результат проверяются отдельно от merge. Выпуск —
только по разрешению пользователя: сохранить доставляемую версию, проверить её
в месте использования; восстановление — новый адресный `revert` своего коммита
после разбора последующих изменений, без уничтожения чужой истории.

**Условный GitHub, в том числе публичный.** Условия: пользователь отдельно выбрал
публичное хранение очищенного кода, один доверенный сопровождающий; секреты/личные
данные не публикуются. Агент готовит ветку `change/<смысл>`, локальные проверки и
описание изменения; push/создание сервера — только при выданном разрешении.
Сопровождающий с правом write объединяет после выбранных проверок и разбора
замечаний. Человек-ревьюер нужен при выбранном правиле/риске, публичность сама
не требует сложной схемы. При нескольких авторах — ветка на изменение и pull
request, права/защита основной ветки и обязательные серверные проверки задаются
явно. Если они недоступны, обязательное объединение ждёт, их не называют пройденными.
После merge принимается интеграция итоговых входов. Релиз: уполномоченный
сопровождающий выбирает коммит/тег и проверяет артефакт; отдельно разрешает
публикацию. Возврат — revert/предыдущий проверенный артефакт по местным правилам,
с выяснением внешнего исхода до повтора. Описанный серверный процесс не равен
проверенным доступам, CI, push или выпуску; фактические проверки перечисляются отдельно.

<a id="shared-index"></a>
### Незавершённая чужая работа и общий индекс

Сначала пройди [безопасный осмотр](#git-inspection):
настройки/атрибуты и необработанные версии, затем допустимый обычный осмотр.
Статус/рабочий diff не являются первым безопасным действием. Сохрани отдельные
байты/режимы чужих рабочих файлов и индексных записей. Перед изменяющей операцией
разбери все обработчики, которые она может вызвать, и обязательные правила проекта.
Получив единственное право Git, перечисли точные имена согласованных файлов.
Используй `git --literal-pathspecs -c core.fsmonitor=false diff --no-ext-diff --no-textconv --cached -- "$file_path"`
и тот же вызов без `--cached` для просмотра согласованных файлов. Передавай
каждый путь отдельным аргументом по [правилу буквального выбора](#git-inspection).
Для новых файлов подготовь точные пути через `git --literal-pathspecs add -- "$file_path"`.
После подготовки проверь выбранные пути и сохранность чужих записей.
Если во всех выбранных файлах согласованы рабочие байты, используй
`git --literal-pathspecs commit --only -m 'Сообщение' -- "$file_path"`.
`--only` берёт рабочие байты выбранных файлов, включая все правки в них.
После коммита сверь его полный состав и прежние чужие индексные объекты и режимы.
Основания команд — в [справке об осмотре Git](../reference/decisions.md#git-history).
Не используй `git add .`, безусловный commit, stash/reset/clean
для освобождения чужого индекса. Если свои и чужие изменения в одном файле,
не применяй рецепт целиком: раздели свой фрагмент по правилам проекта, сохрани
исходный индекс и докажи сохранность; при недостаточной информации коммит
подключения можно отложить с причиной, оставив проверенные файлы/продолжение.
Не останавливай чужую работу и не угадывай её приёмку.

<a id="task-move-git"></a>
### Сохранить уже перенесённую папку задачи

Единственный владелец Git начинает с [безопасного осмотра](#git-inspection).
Из `move --task НОМЕР` возьми `card_paths` и `files`. Рабочая карточка уже
может лежать в `done`, индекс ещё содержать путь из `open`, а последний
коммит (`HEAD`) хранить этот путь с другой редакцией. Сравни каждый слой
по его пути. Ключ `blob` у рабочего файла — идентификатор его сырых байтов
без преобразователей Git. Фактические правила подготовки выясни по атрибутам.
Проверь оставшиеся записи по старым путям, в том числе индексную версию,
которой нет в рабочей папке. Сохрани доказательства того, какие чужие байты
и режимы ожидаются в рабочем дереве и индексе.

Согласуй точные удаления в старой папке и добавления в новой. Включи
только разрешённые файлы и байты. При чужом файле в индексе вне этого набора
используй [порядок работы с общим индексом](#shared-index). В примере владелец
согласовал карточку и отчёт `draft[1].md`. Подставь фактические имена, в том
числе для отчёта с обычным именем. Сохрани каждый путь отдельным аргументом.

```sh
task_move_old_card='docs/tasks/open/T-008-search-study/task.json'
task_move_old_report='docs/tasks/open/T-008-search-study/draft[1].md'
task_move_new_card='docs/tasks/done/T-008-search-study/task.json'
task_move_new_report='docs/tasks/done/T-008-search-study/draft[1].md'

GIT_OPTIONAL_LOCKS=0 git --literal-pathspecs -c core.fsmonitor=false diff --no-ext-diff --no-textconv --no-renames --name-status -- \
  "$task_move_old_card" "$task_move_old_report" "$task_move_new_card" "$task_move_new_report"
GIT_OPTIONAL_LOCKS=0 git --literal-pathspecs -c core.fsmonitor=false diff --no-ext-diff --no-textconv --no-renames --name-status --cached -- \
  "$task_move_old_card" "$task_move_old_report" "$task_move_new_card" "$task_move_new_report"
```

По рабочим файлам и индексу из первоначального осмотра сверь также новые
пути, которых ещё нет в выводе `diff`. После подготовки повтори индексный
`diff` по тем же четырём именам. Сверь подготовленные байты с ожидаемыми,
а чужие записи проверь отдельно в полном индексе. К коммиту переходи при
совпадении выбранных путей, байтов и чужих записей.

```sh
git --literal-pathspecs add -A -- \
  "$task_move_old_card" "$task_move_old_report" "$task_move_new_card" "$task_move_new_report"
```

После сверки подготовленного набора сохрани согласованный перенос.

```sh
git --literal-pathspecs commit --only -m 'Сохранить перенос P/T-008' -- \
  "$task_move_old_card" "$task_move_old_report" "$task_move_new_card" "$task_move_new_report"
```

Если в выбранном файле есть чужая рабочая или подготовленная правка,
согласуй с её владельцем, какие байты переезжают в коммите и где остаётся
подготовленная версия. До этого перенесённую папку можно читать, а шаг Git
остаётся открытым.

После записи проверь полный список изменённых путей в коммите через
`GIT_OPTIONAL_LOCKS=0 git diff-tree --no-renames --no-commit-id --name-status -r HEAD`.
Сверь байты, индексные записи и рабочие байты чужих материалов. Повтори
осмотр по номеру. Исторический
отчёт открывается по исходному коммиту и прежнему пути. Для зависимой
карточки проверь действующую приёмку с сохранённым основанием.

<a id="update-and-rollback"></a>
## Повтор, обновление, возврат и отключение

При каждом действии снова проверь выбранный cwd/вход, нынешний беклог, версию и
владельца записи. Сначала сравни имеющееся с записью подключения в профиле и
Git-основанием; чужой маркер или неизвестное происхождение не означает владение.

**Повтор той же версии.** При одинаковой рабочей части/одном блоке не копируй
шаблоны поверх заполненного профиля/состояния и не добавляй переход. Местные
изменения сохраняются и отражаются как «версия поставки + местные изменения», даже если
файл VERSION тот же. Проверь путь входа и затронутые команды; не создавай вторую
очередь или пустые журналы. Отсутствующий модуль восстанавливай по сравнению,
не считай частичный перенос готовым.

**Подготовка обновления.** Перед существенным блоком открой [делегирование](roles.md#delegation-and-plan). Найди точные три текста: прежнюю поставку, нынешнюю местную редакцию с действующим входом и профилем, новую поставку. Сверь принадлежность блоков, местные правила, старые адреса, зависимости, состав, формы и команды. Хеш сверяет доступный текст. Если исходный текст или происхождение неизвестны, сохрани местное и выясни различия до замены. Подготовь сохранённые исходники, план переключения и возврат. Подготовка возможна при активной попытке, пока рабочая редакция и её входы остаются нетронутыми; новую редакцию тогда получи отдельно. Рабочий клон переключай только в безопасной точке ниже. Если пользователь уже обновил его, используй [вход после pull](#after-pull).

**Безопасная точка.** До переключения установи [владельца записи](roles.md#shared-resources), [фактическую судьбу попыток](recovery.md#resume) и [исход внешних действий](recovery.md#uncertain-outcome). Переключайся вне активного исполнения, использующего эту редакцию. До чтения записей установи режим и [формат](../formats.md#record-versions). Проверь затронутые поручения, мандаты, зависимости и сохранённые входы, в том числе профиль и правила продукта. По [пересмотру](recovery.md#reassess) определи право продолжения и согласованно обнови затронутые действия. При смене общего решения используй существующий `revision_review`. При частичном режиме сохрани проверки агента. Перенос формата или беклога — отдельное переключение.

**Переключение.** Обнови рабочую часть в выбранном размещении, управляемый блок фактического входа или явный старт и заполненный профиль. Проверь обычный вход, override и вложенные папки по [порядку входа](#effective-entry) там, где они применимы. Для старых адресов замени указатель в точке чтения либо перенаправь к эквивалентному смыслу. Исторические ссылки на точную редакцию сохрани. Сохрани местные правила, память, единственный живой источник работ, состояние, попытки, результаты и историю. Перенеси действующие расходные ограничения и запреты, включая запрет новых отдельных платных средств, вместе с источниками решения. При возврате сохрани их тем же порядком. Местные изменения старого кита перенеси в действующий источник продукта либо явно разреши конфликт до замены. Не сбрасывай заполненные записи чистой формой.

Пройди [проверку подключения](#install-check) из фактических рабочих папок, включая читающее поведение и адресные проверки. Сохрани версии/коммиты, местные отклонения, решения, проверки, нерешённое, применимость прежних приёмок и допустимый следующий шаг. `VERSION` указывает базовую поставку, профиль — действующую местную редакцию.

**Возврат.** Установи безопасную точку тем же порядком. Восстанови согласованную рабочую часть и её стартовые переходы, объединив местные изменения после обновления. Сверь заполненный профиль, ссылки, новые записи, историю и право продолжения. Повтори [разбор входов](recovery.md#reassess) и [проверку подключения](#install-check). При возврате к прежнему живому беклогу сначала перенеси накопленные события и согласуй один источник и редактора по [порядку переноса](#partial-and-migration).

**Отключение.** По границам и исходной версии найди только добавленные
блоки/переходы; сравни местные изменения внутри и вне их. Полезную добавленную
местно норму/ссылку сохрани в действующем источнике без неработающего указателя
на удаляемую папку. Не удаляй весь файл override/AGENTS, если он существовал или
получил другие правила. Прежний переход, не созданный подключением, сохраняется.
Если добавленный переход позднее стал нужен ещё для другой местной ссылки,
сохрани эту часть явно. Удали только подтверждённо принадлежащую рабочую часть;
изменённые полезные файлы сначала перенеси в их действующий источник/сохрани.
Чужая папка, решения, результаты, незавершённые задачи и история остаются.
Обнови запись подключения как отключённую; укажи действующий беклог и продолжение.
После проверь достижимость оставшихся ссылок, сохранность прежних/последующих
правок и Git. При повторном удалении отсутствие своего блока — нормальный исход,
а не повод удалить соседний. При возврате снова согласуй пути и создай ровно
один блок/переход; заполненная память продолжается, не сбрасывается.
Удаление инструкций не отменяет внешние действия/данные: неизвестный исход
выясняется отдельно. Неизвестное происхождение файла означает запрет угадывать
его удаление, а не готовность чистить папку целиком.

<a id="after-pull"></a>
### Если пользователь уже выполнил git pull

Получение файлов ещё не означает завершение обновления проекта. Начни с безопасной точки и подготовки сравнения выше; до их проверки не продолжай прежние продуктовые назначения. При неизвестной судьбе исполнений допустимы чтение и восстановление фактов по указанным процедурам, а не объявление попыток завершёнными.

Установи фактические корни продукта и клона, коммит и `VERSION` полученной поставки, действующий вход и заполненный профиль. Для осмотра обоих Git-корней используй [безопасный порядок](#git-inspection). Прежнюю поставку определи по сохранённому пользователем коммиту и записи подключения. При расхождении выясни, какая редакция действительно использовалась; не считай нынешний `HEAD` или `HEAD~1` прежней установленной версией. Если коммит не передан, проверь основание из профиля; журнал перемещения ветки может помочь найти кандидата, но не подтверждает его применение в продукте.

Прежние файлы читай без переключения рабочего дерева: например, `git -C .ai-dev-kit show <прежний-коммит>:kit/procedures/adapt.md`, подставив проверенный коммит и путь. Если объекта нет, получи точный источник из известного репозитория либо сохранённой копии. Пока исходное состояние не установлено, сохрани документы продукта, перечисли недостающее и не заменяй неизвестные блоки.

Сопоставь полученную поставку с действующим подключением и выполни нужную часть «Переключения» выше. Для 0.3.0 начни с [адресной проверки](#update-to-0-3-0). Прежние проверки [0.2.0](#update-to-0-2-0) и [p5](#update-to-p5) доступны по фактической редакции. Правила продукта сопровождай по [единому порядку](project-rules.md#maintain-rules). Если подключение уже соответствует той же редакции, примени «Повтор той же версии»; правки ради самого обновления не нужны. Заверши проверкой подключения и записью результата в существующем месте памяти. Отдельно укажи файловую проверку, явное чтение в текущем чате и наблюдение автоматической загрузки в новом чате; одно не заменяет другое.

<a id="update-to-0-3-0"></a>
### Обновление с 0.2.0 до 0.3.0

1. Установи прежнюю редакцию по записи подключения или Git-коммиту.
   Скопированные файлы сравни с прежним комплектом и новой рабочей частью.
   Для клона после `pull` прочитай старую редакцию через `git show`.
   Проверь [полный рабочий состав](#placement) по фактическому размещению.
2. Сохрани местные правила и выбери способ обновить действующий вход либо
   явный старт. Если прежний профиль был существенным входом, сохрани его
   точную редакцию по тому же пути и подключи отдельный профиль выбора.
   Запиши в нём размещение, версию и Git-коммит либо контрольные суммы.
   До смены источника прочитай прежний список штатной командой. Для
   совместимого файла состояния проверь `check --profile` с его форматом
   и адресом. Для стороннего списка сохрани его команду и ручную сверку.
3. Если поручено перейти на карточки, пройди [подготовку](#partial-and-migration)
   и [прямое переключение](#switch-to-task-cards). В обновлённом профиле
   оставь явный маршрут чтения прежних записей. Для выбранных карточек
   проверь `check`, `tasks`, заявленные действия и `overview` из рабочего
   размещения. Если переход отложен, нынешний источник и допустимая работа
   остаются указаны в профиле.

<a id="update-to-0-2-0"></a>
### Переход к 0.2.0

Применяй после установления прежней редакции и безопасной точки. Проверь полноту полученного комплекта, включая `tools/versions.py`. Если вход и профиль ещё не переведены на структуру p5, сначала примени [её адресную проверку](#update-to-p5) по фактическим различиям. У уже подключённого p5 новые разделы профиля и копирование исследовательской процедуры в проект не требуются.

В профиле зафиксируй версию и коммит полученной поставки, а формат рабочих записей укажи по их фактическому содержимому. Совместимые прежние обозначения определены [договором форматов](../formats.md#record-versions); не переписывай существующие записи и историю только ради номера. Новые записи создавай по текущим формам. Для штатного источника выполни обычный `check` и проверь затронутые входы, ссылки и применимость прежних поручений. Для частичного режима используй предусмотренные проверки агента. При предстоящем исследовании или ревью открой соответствующую ветвь [рабочей процедуры](workflow.md#research-review).

При планировании возврата учти, что код прежних выпусков не читает новые обозначения форматов. Сохрани исходную редакцию и проверь все используемые текущие и исторические записи по «Возврату» выше; не обещай откат одной заменой номера.

<a id="update-to-p5"></a>
### Переход к 0.1-p5

Применяй этот список после установления прежней версии и местных отличий. Для p3 и иных редакций проверь их фактическую процедуру; не подставляй предположения о p4.

1. Сравни управляемый блок действующего входа с [новым фрагментом](../entry/AGENTS.fragment.md). Он ведёт к разделу профиля «Подключение и единственные источники» и карте [ближайшего действия](../README.md#entry-routes). Подставь реальные пути. Обработай override, вложенные папки или явный старт по [правилу входа](#effective-entry); весь файл входа формой не заменяй.
2. Сопоставь заполненный профиль с [актуальной формой](../templates/project.md). Добавь недостающие указатели и раздел «Проектные нормы по области и действию», указывая для существующих правил область, момент чтения и владельца. Устрани прежнее требование всегда читать все большие процедуры, если оно принадлежало старому блоку комплекта; местное требование не считай устаревшим без проверки его смысла. При отсутствии проектной нормы не создавай её ради заполнения формы. Нужные профильные разделы выбираются по [старту и действию](workflow.md#start-and-resume).
3. Проверь действующие ссылки из входа, профиля, поручений и проектных норм. Номер прежнего раздела не означает тот же смысл в p5. Сопоставь определение с новой [картой маршрутов](../README.md#entry-routes), включая правила продукта в `project-rules.md` и справочные основания в `reference/decisions.md`. Исторические ссылки на старый коммит сохраняй как историю.
4. Проверь формат рабочих записей по [договору версий](../formats.md#record-versions). Сама p5 не меняет формат `0.1-p2` и не требует пересоздавать задачи, результаты или состояние; для старого p1 действует его ограниченный путь. Изменение профиля и ссылок всё равно требует проверки существенных входов и права продолжения по «Безопасной точке» выше.
