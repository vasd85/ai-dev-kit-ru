# Применить комплект к разрешённому проекту

Эту процедуру выполняет агент по поручению пользователя. Пользователь описывает
потребность и выбирает существенные продуктовые решения, архитектуру и расходы.
Файлы копирует, профиль заполняет, обычные проверки и исправления выполняет агент.
Подключение не разрешает реализовать весь будущий продукт или опубликовать его.
Нужны локальные Git и Python 3; без Git полная диагностика не поддержана.

## 1. Установить исходное состояние до записи

Прочитай правила разрешённого проекта, найди его Git-корень и выбранную рабочую
папку. У нового проекта сначала сохрани идею, разрешённую подготовку и неизвестное;
создавай локальную Git-историю только в разрешённой папке. Для существующего найди
архитектурные документы, правила разработки, реальные задачи Todo/Doing/Done,
их владельцев, приёмки и проверки. Пустой новый `state.json` их не заменяет.
Не запускай неизвестные команды, установку, хуки или генераторы ради осмотра.

Прочитай Git-правила проекта. `status` и рабочий `diff` могут вызвать
`filter.<имя>.clean` или `filter.<имя>.process`. Параметры `--no-ext-diff`,
`--no-textconv` и `core.fsmonitor=false` подавляют другие механизмы и не защищают
от этих преобразователей. Поэтому первоначальный осмотр идёт в следующем порядке.
Это маршрут для доверенной локальной среды без конкурентной подмены файлов,
не песочница для произвольного враждебного окружения.

**А. Установить источники, не вызывая обработчики.** Чтением файлов найди корень,
реальный каталог Git (учти gitfile/common-dir) и выбранную папку. Не перенаправляй
команды на другой репозиторий переменными окружения. Установи применимые
`GIT_CONFIG_*`, `GIT_ATTR_*`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`,
объектные перенаправления и параметры запуска; не раскрывай секреты в журнале.
Ниже команды из установленного корня с его настоящим окружением. Неизвестное
перенаправление сначала разбери. Для диагностики `check` сохраняются её более
узкие ограничения из README; способность вручную прочитать источник их не снимает.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never config --includes --show-origin --show-scope --list
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never ls-files --stage -z
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never ls-files --cached --others --exclude-standard -z
```

`config` здесь только читает значения и подключаемые файлы, не выполняет записанные
команды. Учитывай system/global/local, при наличии worktree, `include/includeIf`
и окружение/параметры команды. Происхождение и порядок значений важны: не выбирай
первое совпадение. Прочитай применимые подключения, включая условия; отсутствующий
или недоступный источник не объявляй пустым по одному успешному коду команды.
`ls-files --stage` даёт режим, ID объекта и стадию каждой индексной записи без
освежения рабочих файлов. Второй список добавляет неигнорируемые новые пути.
Игнорируемое, значимое внешнее и будущие пути подключения добавь явно по файловому
осмотру; список Git не является полным обходом всех данных.

Для каждого затронутого пути, подставив вместо `path/to/file` настоящий путь от
корня, прочитай эффективные атрибуты и их индексный вариант:

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never check-attr -z filter diff text eol working-tree-encoding ident -- path/to/file
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never check-attr --cached -z filter diff text eol working-tree-encoding ident -- path/to/file
```

`check-attr` сообщает значения, не выполняет clean/process/textconv. Имя фильтра
может быть любым и может прийти через макрос. Проверь `.gitattributes` в папке
файла и предках до корня, индексный fallback при отсутствии рабочего файла,
`$GIT_DIR/info/attributes`, `core.attributesFile` (либо стандартный пользовательский
файл `$XDG_CONFIG_HOME/git/attributes`, по умолчанию `$HOME/.config/git/attributes`)
и системный файл установки Git. `info/attributes` имеет высший приоритет;
более близкий `.gitattributes` перекрывает дальний, пользовательский/системный —
ниже. `check-attr` учитывает доступные применимые источники; его вывод не доказывает
доступность каждого из них. Установи пути/доступность, прочитай относящиеся правила
и сообщения об ошибках; недоступное или неустановленное сохрани как неизвестное.
Отключённый окружением источник не выдавай за проверенный в обычном окружении.

**Б. Собрать доступные версии без преобразования.** До разбора фильтров допустимы
перечисление/чтение обычных файлов и режимов, названные выше команды, а также
чтение локальных объектов ниже. Сохрани раздельно рабочие байты, индексные
режимы/объекты/стадии, HEAD и признаки незавершённых merge/rebase/cherry-pick в
служебной папке. Не используй для этого `status`, рабочий diff, `hash-object --path`,
`cat-file --filters/--textconv`, refresh/update-index, add или проектные команды.
Не заходи командами Git в подмодули; неизвестное в них фиксируется отдельно.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 GIT_NO_REPLACE_OBJECTS=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never ls-tree -rz --full-tree HEAD
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 GIT_NO_REPLACE_OBJECTS=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never cat-file blob "$object_id"
```

`object_id` агент задаёт точным ID blob из индекса или дерева коммита, не путём с
догадкой о стадии. Сравни индекс с HEAD по ID/режимам; содержимое каждого blob —
отдельно с рабочими байтами. Это байты сохранённого объекта без фильтра, не результат
clean рабочего файла. Даже равенство байтов не доказывает Git-эквивалентность при
неизвестном преобразовании (включая text/eol/encoding). Отсутствующий HEAD нового
проекта допустим и так записывается. Отсутствующий/внешний объект, ошибка чтения
или неподдерживаемое устройство Git остаются неизвестными; сеть/получение объектов
не запускаются. Временные `GIT_NO_LAZY_FETCH=1` и `protocol.allow=never`
запрещают получение по протоколам; `GIT_NO_REPLACE_OBJECTS=1` в командах объектов
показывает исходные объекты без refs/replace, а не их обычное замещённое представление. Эти команды не обещают поддержку partial clone/worktree программой
`check` и не устанавливают полностью обычный Git-status.

**В. Разобрать и продолжить.** По эффективному `filter` найди все применимые
`filter.<имя>.clean`, `.process`, `.required` и при записи `.smudge`; process имеет
приоритет над clean. Прочитай команду и доступный код/условия/внешние зависимости,
не запускай неизвестное для выяснения поведения. Аналогично установи diff.external,
драйверы diff/textconv, fsmonitor, а перед записью hooks и signing. Неизвестный,
обязательный или неподдерживаемый обработчик сохраняет ограничение затронутой
операции, а не запрещает все проекты с фильтрами. Дальше можно читать доступные
версии и подготовить разрешённые файлы подключения с точной областью правок.
Следующий шаг — разобрать конкретный источник/обработчик; коммит можно отложить
с причиной. Существенное недостающее разрешение решается по правилам проекта,
обычные технические детали агент выясняет сам.

Когда для всей области команды установлено отсутствие преобразователя либо
конкретный преобразователь изучен и его исполнение допустимо в выданных полномочиях,
можно выполнить обычный осмотр ниже. Наличие безвредного имени или одного
изученного фильтра не разрешает другие. Не запускай корневой status, если разобрана
только часть путей; при неизвестном оставайся на маршруте А–Б.

```sh
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never status --short --ignore-submodules=all
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never diff --no-ext-diff --no-textconv --ignore-submodules=all
GIT_OPTIONAL_LOCKS=0 GIT_NO_LAZY_FETCH=1 git --no-pager -c core.fsmonitor=false -c protocol.allow=never diff --no-ext-diff --no-textconv --ignore-submodules=all --cached
```

Подмодули здесь исключены, их состояние не объявляется проверенным. Подавление
внешнего diff/textconv/fsmonitor действует только для этих вызовов и не отключает
clean/process. Не вноси постоянных отключений фильтров, hooks или signing и не
обходи обязательные проверки настоящей записи. Читающий маршрут сам не разрешает
исполнение проектного кода. Перед add/commit повторно проверь относящиеся условия:
изменяющая команда может освежать и другие записи индекса даже при точных путях.

Установи владельца изменяющих операций и судьбу прежних исполнителей: отсутствие
сообщения не доказывает остановку. Чужие правки/индекс не откатывай и не включай в
свой коммит. При чужом незавершённом merge/rebase/cherry-pick коммит подключения
отложи. Сохрани исходные байты/режимы изменяемых файлов и понятную исходную точку
Git. Не создавай коммит всей папки по умолчанию. Детальный порядок записи — §8.

Основания команд и источников: [git config](https://git-scm.com/docs/git-config),
[git check-attr](https://git-scm.com/docs/git-check-attr),
[gitattributes](https://git-scm.com/docs/gitattributes),
[git ls-files](https://git-scm.com/docs/git-ls-files). Адресная сверка: 7 ноября 2026.

## 2. Найти фактически читаемый вход

Для каждой разрешённой рабочей папки запиши цепочку от корня проекта до неё.
В каждой папке Codex выбирает максимум один непустой файл: `AGENTS.override.md`,
затем `AGENTS.md`, затем настроенные резервные имена. Вложенные правила имеют
более высокий приоритет. Глобальные инструкции тоже действуют; их не меняют.
Без найденного корня документация описывает проверку только текущей папки.
Не угадывай недоступную конфигурацию/границу корня; зафиксируй неизвестное.

Основание проверено 6 ноября 2026 по [официальной документации OpenAI](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
(исходный адрес `https://developers.openai.com/codex/guides/agents-md`). Цепочка
собирается при старте, общий предел по умолчанию 32 KiB, он может быть изменён.
Проверь доступные местные настройки, объём и возможное усечение. Одной Markdown-
ссылки недостаточно: блок должен предписывать агенту явно прочитать файлы.
Проверка этой цепочки по файлам не является наблюдением нового чата.

Если в одной папке существуют оба файла, блок только в обычном `AGENTS.md`
недостижим без перехода из выбранного override. Достаточны три варианта:

1. Добавить короткий блок в действующий файл, сохранив прежние правила.
2. Переиспользовать или добавить явный переход из него к обычному файлу с блоком.
   Например: «Явно прочитай раздел ai-kit в корневом AGENTS.md; прежние правила
   этого override имеют приоритет в своей области». Не загружай весь обычный файл,
   если это возвращает намеренно отменённые им правила. Сохрани область исключений.
3. Если действующий вход менять запрещено, подготовить явный текст начала чата
   из §6. В недействующем файле ссылку ради вида не добавляй. Автоматическое
   подключение следующей сессии не заявляй.

Проверь более глубокие переопределения. Корневой блок не доказывает пригодность
для любой вложенной папки. Относительные пути блока ниже означают пути от Git-
корня. Документируй этот корень и разрешённые рабочие папки; не меняй смысл путей
при запуске из `services/api`. Текущая сессия после применения явно перечитывает
новый блок, руководство, профиль и беклог, не ожидая перезагрузки инструкций.

## 3. Выбрать размещение и единственные источники

При копировании рабочей части штатно правила лежат в `.ai-kit/`, память — в
`docs/ai-work/`. Для полного Git-клона из README используй `.ai-dev-kit/kit/`
непосредственно, без второй копии рабочей части. При конфликте
сравни содержимое, происхождение и принадлежность. Чужую `.ai-kit/`, профиль,
очередь или блок не перезаписывай. Достаточно свободных мест, например
`support/agent-kit/` и `planning/assistant/`. Согласуй все указатели и команды.
Файловые пути JSON всегда относительно Git-корня; ссылки между Markdown-
файлами обычно относительно содержащего их файла, если явно не указано иное.

Полная рабочая часть — ровно эти 15 файлов, с сохранением структуры:

```text
README.md
VERSION
entry/AGENTS.fragment.md
formats.md
procedures/adapt.md
procedures/workflow.md
procedures/roles.md
procedures/recovery.md
templates/project.md
templates/state.json
templates/work.md
templates/result.json
tools/kit.py
tools/read_support.py
tools/records.py
```

При копировании переноси эти файлы из полученной поставки; при Git-подключении
они уже находятся в клоне. Не устанавливай Python-модуль. Три `tools/*.py`
нужны рядом. Тесты изготовления и `examples/` остаются в исходной поставке,
в том числе внутри полного клона; их код/учебные задачи не становятся частью
реализации или поручениями продукта.
README содержит отдельно обозначенные команды для полной поставки; для работы
в продукте они не нужны. Никакие исследования или прежняя история чата не нужны.

**Git-клон внутри проекта.** Установи два разных корня: корень продукта и
`.ai-dev-kit/` — корень поставки. Все команды/пути состояния продукта относятся
к первому; в частности `check --root` получает корень продукта. Вход и команды
настрой на `.ai-dev-kit/kit/`, формы памяти заполни вне клона. При подключении
сохрани правила продукта и добавь `/.ai-dev-kit/` в его `.gitignore`, если такого
исключения ещё нет. Сначала убедись, что путь не занят чужими данными и не
отслеживается продуктом; существующий tracked-каталог или подмодуль нельзя
молча удалять из индекса. Не добавляй вложенный репозиторий как случайный
подмодуль и не удаляй его `.git`. При другом размещении измени все пути и исключение.

Запиши в профиле URL источника, точный коммит клона, `VERSION`, местные отклонения
и проверенную команду. Диагностика входов продукта не подтверждает игнорируемый
клон: агент отдельно сверяет его коммит и местные правки. Не обновляй его во время
активного исполнения. При работе над самим комплектом его проверяемые исходники
должны быть в отдельном задании и Git-корне поставки. Правила конкретного продукта
сохраняй в его действующих источниках; общие файлы клона для этого менять не нужно.
Повтор и обновление выполняются по §9 с сохранением продуктовой памяти.

Существующие архитектура и `CONTRIBUTING.md` сохраняют нормативный смысл;
профиль ссылается на них, не создаёт вторую редактируемую норму.
Выбери подходящий режим после содержательного сопоставления:

| Режим | Что сохранить и что установить |
| --- | --- |
| Подходит штатный формат/иная структура | Сохранить пути и данные, настроить указатели и `--state`; проверить фактический формат и команды |
| Нужны дополнения процесса | Предложить минимальное недостающее условие в действующем источнике; существенную смену обязанностей согласовать |
| Частичное применение | Сохранить старый единственный беклог; перечислить ручные проверки агента, место их результатов и запреты; существенный компромисс выбирает пользователь |
| Выбран перенос или адаптер | До переключения подготовить соответствие и возврат; отдельно оценить новый программный адаптер, он не появляется от переименования статусов |

Если обязательное условие обеспечить нельзя, соответствующее действие остаётся
заблокированным. Частичный режим не обходит ошибку полной диагностики.

## 4. Записать новый проект от идеи

Скопируй `templates/project.md` в выбранную память, заполни факты и неизвестное.
Скопируй чистую `templates/state.json`, замени ID/роль/сессию/профиль и ближайшую
цель. Форма не содержит учебной работы, активного писателя и приёмки. Укажи
разрешённую подготовку и ближайший вопрос в профиле/`continuation`; будущие идеи
можно хранить как `candidate`. Не выдумывай стек, тесты или разрешение писать код.
Непустой список `iterations` на этом этапе описывает подготовку, а не обещанный
полный выпуск. Подробное поручение появляется, когда ясны цель и полномочия.

Для одной маленькой работы достаточно одного встроенного поручения/результата
в общем состоянии и профиля. Функция, несколько сессий, пустые журналы, отдельный
файл каждой операции и новый автотест не обязательны. Используй `templates/work.md`
как инструкцию заполнения по `formats.md`. `templates/result.json` — форма с
подсказками, не успешно проверенный факт; заполняй её только после реальной проверки.
Учебное поручение нормализации находится лишь в `examples/single-task.state.json`
полной поставки, в продукт автоматически не копируется.

## 5. Подключить и проверить

После выбора источников перенеси и адаптируй `entry/AGENTS.fragment.md` в выбранный
вход либо обеспечь переход. Замени пути и маркер `product` на местные при нужде.
Сохрани прямое правило делегирования и выбора модели. Все пути к процедурам
должны вести к выбранному размещению, в том числе `.ai-dev-kit/kit/` при Git-клоне.
Для чужого беклога назови его вместо штатного `state.json` и укажи точку
продолжения внутри него или профиля.

В профиле сохрани версию `VERSION`, формат записей, фактическую цепочку/cwd,
места файлов, точные добавленные блоки/переходы, прежний текст или Git-основание,
источник поставки и исходные хеши. Это основание повтора/обновления/удаления,
не отдельная база установок. Не включай изменяемую запись подключения в чужие нормы.

Проверь возможности среды по [правилам ролей](roles.md) и запиши их в профиль
по разделу «Возможности исполнения» [формы профиля](../templates/project.md).
Проследи из выбранного файла или явного стартового текста путь к руководству,
правилам ролей и рабочего порядка, заполненному профилю, ровно одному беклогу
и точке продолжения. Проверь исходные инструкции и чужие данные
сравнением до/после. Явно перечитай этот путь в текущем чате.
Из канонического Git-корня, при штатных путях, выполни:

```sh
GIT_OPTIONAL_LOCKS=0 python3 -B .ai-kit/tools/kit.py check --root "$PWD" --state docs/ai-work/state.json
```

При других путях подставь фактические. Канонический корень не содержит symlink;
пути записей не содержат `..`. Из вложенной папки передай полный канонический
корень и точный путь программы, `--state` по-прежнему от корня.
При изготовлении, проверке подключения/обновления или конкретном новом сомнении
подтверди читающее поведение: до/после проверяемого вызова сравни исходники,
память, рабочие данные, индекс/HEAD и служебные файлы Git. То же требуется при
испытании нового первоначального маршрута §1. Копирование и адаптация намеренно
меняют папку: отдельно проверь точный разрешённый набор правок и сохранность
остального. В штатной работе неизменённым проверенным инструментом выполняй
обычный `check` на предусмотренных переходах; полные снимки всей папки/Git-истории
перед каждым назначением/приёмкой без нового основания не нужны. Диагностика
только читает. Код 0 не доказывает качество продукта или полноту задач.
Чужой неподдерживаемый беклог не подменяй пустой формой ради нуля.

Запиши реальные команды продукта с cwd, условиями, результатами и ограничениями.
Неизвестная команда остаётся неизвестной до допустимого запуска. Отдельно сообщи
пользователю, что подключено, что можно продолжать и что ещё не разрешено.

## 6. Готовые запросы

Первое применение (будущий пользователь подставляет два пути; это не разрешение
применять комплект к какому-либо продукту сейчас):

> Примени комплект из `/путь/к/kit/README.md` к разрешённому проекту
> `/путь/к/проекту`, рабочая папка — его корень. Сначала прочитай руководство
> и процедуру применения. Сохрани прежние правила, архитектуру, задачи и чужие
> изменения. Сам подготовь профиль, один источник работ, подходящий Git-процесс
> и достижимый вход. Проверь подключение и сохрани продолжение для новой сессии.
> Реализовывать будущие функции и публиковать проект этим не поручено.

Когда вход менять нельзя (агент заполняет фактические пути и сохраняет текст):

> Работай в `/канонический/корень/проекта`, рабочая папка — `services/api`.
> Соблюдай действующие инструкции этой цепочки: [точный список]. Дополнительно
> явно прочитай `[корень]/support/agent-kit/README.md`,
> `[корень]/planning/assistant/project.md` и единственный беклог `[точный путь]`.
> Прочитай `[корень]/support/agent-kit/procedures/roles.md` и
> `[корень]/support/agent-kit/procedures/workflow.md`. Существенную отделимую
> работу делегируй в разрешённых границах. До начала покажи план исполнения
> и выбери настройки помощника отдельно от настроек текущего чата.
> Продолжи с [точный раздел/continuation], соблюдая записанные ограничения.

Этот запрос действует при его явном использовании. Новая сессия сама его не
получит. Файловая сверка достижимости и реальное наблюдение загрузки новой
пользовательской сессией — разные свидетельства; второе не выдумывай.

## 7. Существующий беклог и перенос

До выбора режима пройди реальные намеченные, активные и завершённые записи.
Сохрани в профиле путь, прочитанную редакцию, смысл статусов, редакторов,
принимающего и фактические свидетельства. Например, в `Todo → Doing → Done`
последнее может означать только окончание кода. Тогда Done остаётся историческим
утверждением автора, а не принятой проверкой. Дополнение той же карточки полями
«проверка / принимающий / ограничения / следующий шаг» достаточно, если это
согласованный порядок. Не навязывай новый статус или человека-ревьюера.

При частичном режиме старый беклог остаётся единственным источником работ.
Профиль хранит собственный разбор агента: какие ID проверены, зависимости,
действующие владельцы и запись, приёмка/свидетельства, неизвестное, итог/запреты,
следующий допустимый шаг. Это результат проверки названной редакции, а не вторая
редактируемая очередь. При изменении карточки результат устаревает и пересматривается.
Не запускай `check` на пустом штатном состоянии и не называй это проверкой беклога.
Программа может проверить отдельную совместимую область, только если её смысл и
границы явно заданы; полный чужой формат она от этого читать не начинает.
Отсутствующая обязательная приёмка запрещает зависимое назначение. Неизвестный
писатель удерживает запись. Чтение/анализ может продолжаться независимо.

Если выбран перенос, до переключения составь таблицу старый ID → новый ID,
статус/смысл, владелец/попытка, зависимости, исторические результаты/степень
проверенности. Непроверенный Done можно перенести как `submitted` только с
реальным результатом по штатному формату; иначе — `blocked` с причиной и шагом
восстановления свидетельств, сохранив прежнее утверждение в истории/профиле.
Не создавай фиктивные коммиты, попытки, проверки и приёмки задним числом.
Старые действующие исполнители не объявляются остановленными от смены формата.
Если источник нельзя выразить без потери этих свойств, перенести пока нельзя.

Сначала подготовь копию и проверь соответствие открытых/завершённых работ,
владельцев, зависимостей и истории. После установленной передачи редактора
сохрани старый источник неизменённым в истории и замени живой вход указателем
на новый с датой/основанием переключения. Сохрани исходный коммит/байты и способ
возврата. При возврате учти все новые события после переключения, согласуй один
активный источник и редактора; простое восстановление старого списка потеряет
новые результаты. Адаптер чтения другого формата отдельно оценивается и проверяется;
его разработка не является обязательной частью ручной процедуры.

## 8. Конкретный Git-процесс

Если правила уже в `CONTRIBUTING.md` или другом нормативном файле, профиль
ссылается на него и фиксирует проверенные команды. Изменение правила делается
в его источнике. Выбор сервера/публичности сам не разрешает передачу данных.
Ниже условные примеры, а не настройки каждого продукта.

**Локальный проект одного автора.** Условия: только локальная история, один
агент пишет, пользователь выбрал результат и разрешил местную реализацию.
`main` достаточна; для рискованной работы — временная ветка. Агент сохраняет
входы и поручение до проверки, затем результат/приёмку отдельным коммитом.
Перед объединением сравниваются итоговые входы, выполняются необходимые тесты;
тот же текст входов после merge не требует повторять все тесты без основания.
Приёмка поведения и общий результат проверяются отдельно от merge. Выпуск —
только по разрешению пользователя: сохранить доставляемую версию, проверить её
в месте использования; восстановление — новый адресный `revert` своего коммита
после разбора последующих изменений, без уничтожения чужой истории.

**Условный GitHub, в том числе публичный.** Условия: пользователь отдельно выбрал
публичное хранение очищенного кода, один доверенный сопровождающий; секреты/личные
данные не публикуются. Агент готовит ветку `change/<смысл>`, локальные проверки и
описание изменения; push/создание сервера — только при выданном разрешении.
Сопровождающий с правом write объединяет после выбранных проверок и разбора
замечаний. Человек-ревьюер нужен при выбранном правиле/риске, публичность сама
не требует сложной схемы. При нескольких авторах — ветка на изменение и pull
request, права/защита основной ветки и обязательные серверные проверки задаются
явно. Если они недоступны, обязательное объединение ждёт, их не называют пройденными.
После merge принимается интеграция итоговых входов. Релиз: уполномоченный
сопровождающий выбирает коммит/тег и проверяет артефакт; отдельно разрешает
публикацию. Возврат — revert/предыдущий проверенный артефакт по местным правилам,
с выяснением внешнего исхода до повтора. Описанный серверный процесс не равен
проверенным доступам, CI, push или выпуску; фактические проверки перечисляются отдельно.

**Незавершённая чужая работа и общий индекс.** Сначала выполни маршрут §1:
настройки/атрибуты и необработанные версии, затем допустимый обычный осмотр.
Статус/рабочий diff не являются первым безопасным действием. Сохрани отдельные
байты/режимы чужих рабочих файлов и индексных записей. Перед изменяющей операцией
разбери все обработчики, которые она может вызвать, и обязательные правила проекта.
Получив единственное право Git, выбери точные пути подключения. Если в выбранных файлах нет чужих
подготовленных или неподготовленных правок, локальный `git commit --only --
<точные-пути>` позволяет сохранить её в индексе. Сначала проверь по штатному
`git -c core.fsmonitor=false diff --no-ext-diff --no-textconv --cached -- <свои-пути>`
и той же командой без `--cached`, после — состав коммита
и прежние чужие индексные объекты/режимы. Учитывай новые файлы: их сначала добавляют
по точным путям. `--only` берёт рабочие байты выбранных файлов: свой подготовленный
фрагмент не защищает чужую правку в том же файле. Перечисляй конкретные собственные
файлы, без широких каталогов/pathspec с чужим содержимым. Основание —
[git diff](https://git-scm.com/docs/git-diff) и [git commit](https://git-scm.com/docs/git-commit),
сверено 6 ноября 2026. Не используй `git add .`, безусловный commit, stash/reset/clean
для освобождения чужого индекса. Если свои и чужие изменения в одном файле,
не применяй рецепт целиком: раздели свой фрагмент по правилам проекта, сохрани
исходный индекс и докажи сохранность; при недостаточной информации коммит
подключения можно отложить с причиной, оставив проверенные файлы/продолжение.
Не останавливай чужую работу и не угадывай её приёмку.

## 9. Повтор, обновление, местное изменение и удаление

При каждом действии снова проверь выбранный cwd/вход, нынешний беклог, версию и
владельца записи. Сначала сравни имеющееся с записью подключения в профиле и
Git-основанием; чужой маркер или неизвестное происхождение не означает владение.

**Повтор той же версии.** При одинаковой рабочей части/одном блоке не копируй
шаблоны поверх заполненного профиля/состояния и не добавляй переход. Местные
изменения сохраняются и отражаются как «версия поставки + местные изменения», даже если
файл VERSION тот же. Проверь путь входа и затронутые команды; не создавай вторую
очередь или пустые журналы. Отсутствующий модуль восстанавливай по сравнению,
не считай частичный перенос готовым.

**Обновление.** Найди три точных текста: прежняя поставка, нынешний местный и
новая поставка. Git-история или сохранённые исходные байты/хеши дают основание
сравнения. Хеш без доступных исходных байтов не разрешает угадать конфликт.
Обновляй рабочую часть и вход только вне активного исполнения, использующего
эту редакцию. Сначала установи судьбу прежних попыток по [восстановлению](recovery.md).
Для Git-подключения сначала получи и изучи новую редакцию отдельно от активных
поручений; не выполняй безусловный `pull` при каждом продолжении. После перехода
запиши новый коммит поставки в профиле и проверь подключение. Клон остаётся
отдельным репозиторием; обновление не переносит в него память продукта.
Сначала составь различия и сохрани местный вариант. Если менялось и местно,
и в новой поставке, сопоставь смысл и объедини в своих полномочиях; норму продукта
не меняй ради номера версии. Разбери новые зависимости и список переноса.
При переходе на `0.1-p4` сравни и обнови принадлежащий подключению блок
в действующем входе или явный стартовый текст. Сохрани местные правила и
переходы. Дополни заполненный профиль сведениями о возможностях исполнения
и месте сохранения планов. Состояние, результаты и сведения о прежних
исполнителях сохраняй. Запиши
исходную/итоговую версию, местные отклонения, решения, затронутые поручения,
проверки и возврат. При изменении общего решения используй `revision_review`
и процедуру восстановления. Повтори проверки §5. Если изменившийся вход
или профиль влияют на применимость текущего действия, разбери точное
обязательство по [рабочему порядку](workflow.md). Пока передача по старым
входам не подтверждена, сохрани прежние приёмки и заяви `inspect` с причиной
и шагом перепроверки. После обновления `VERSION` описывает базовую поставку,
профиль — фактический местный вариант.

**Удаление/откат.** Это отключение принадлежащего входа/рабочих файлов, а не
удаление памяти продукта. По границам и исходной версии найди только добавленные
блоки/переходы; сравни местные изменения внутри и вне их. Полезную добавленную
местно норму/ссылку сохрани в действующем источнике без неработающего указателя
на удаляемую папку. Не удаляй весь файл override/AGENTS, если он существовал или
получил другие правила. Прежний переход, не созданный подключением, сохраняется.
Если добавленный переход позднее стал нужен ещё для другой местной ссылки,
сохрани эту часть явно. Удали только подтверждённо принадлежащую рабочую часть;
изменённые полезные файлы сначала перенеси в их действующий источник/сохрани.
Чужая папка, решения, результаты, незавершённые задачи и история остаются.
Обнови запись подключения как отключённую; укажи действующий беклог и продолжение.
После проверь достижимость оставшихся ссылок, сохранность прежних/последующих
правок и Git. При повторном удалении отсутствие своего блока — нормальный исход,
а не повод удалить соседний. При возврате снова согласуй пути и создай ровно
один блок/переход; заполненная память продолжается, не сбрасывается.
Удаление инструкций не отменяет внешние действия/данные: неизвестный исход
выясняется отдельно. Неизвестное происхождение файла означает запрет угадывать
его удаление, а не готовность чистить папку целиком.
