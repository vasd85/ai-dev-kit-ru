# Связанные работы, остановка и продолжение

Это учебные данные для проверки записей и процедур `0.1-p2`. Они не являются поручением разрабатывать личный продукт и не измеряют эффективность агентной команды. Проверки используют новые временные папки и локальный Git; старые свидетельства не заменяются.

В примере различаются историческая приёмка и текущее разрешение. Приёмка сообщает, какой результат был принят на определённых входах. Действие в `actions` сообщает, какие основания нужны сейчас. Успешное чтение заблокированной записи не означает разрешение её реализации.

## Вход через применённый комплект

Сначала по [маршруту подключения](../README.md#nav-s01) выбери Git-корень,
рабочую папку и действующий вход. Перенеси [рабочую часть](../procedures/adapt.md#placement), заполни профиль и единственный беклог. Из действующего входа открой [карту](../README.md#entry-routes) и пройди путь до нужного действия.
Учебные условия ниже заданы авторами сценария, не реальным пользователем.

У новой идеи нет автоматической нормализации строки: `templates/state.json`
пуст по работам/действиям. Сначала сохраняются цель, неизвестный стек и вопросы,
разрешённая подготовка и ближайший шаг. Отдельное условие малой правки разрешает
заменить одну подпись; достаточно точного чтения текста, одного поручения и
встроенного результата без функции, нового тестового модуля и команды исполнителей.
Прежнее поручение нормализации вынесено в `single-task.state.json`: это пример,
его переносят в учебный сценарий только сознательно, заполняя реальные входы.

Два приращения: первая общая проверка принимает сохранение книги. Вторая добавляет
заметки и заново подтверждает сохранность книги на новой версии; обе исторические
приёмки остаются, вторая интеграция не переписывает первую. Для самостоятельной
функции общий вход ведёт к одному местному `local_state`: подготовка, реализация,
местная приёмка, затем отдельная общая интеграция и закрытие с передачей знаний.
Малая следующая правка возвращается в общий беклог без восстановления функции.

## Проверить переносимый код

Начни с [проверки полной поставки](../procedures/adapt.md#full-kit-check).

Тесты создают свои временные репозитории. Они запускают настоящий процесс `kit.py check`, а окончательные результаты относятся к сохранённым Git-входам. Качество критериев и правдивость сохранённых фактов всё равно разбирает агент. Команда не применяет комплект к действующему продукту.

Связанный R1 можно сохранить отдельно для чтения в новом каталоге:

```sh
r1_parent="$(mktemp -d)"
python3 -B kit/tests/test_records.py --example "$r1_parent/repo"
```

Генератор печатает канонический корень, путь состояния и коммиты C1/C2. Существующий каталог он не заменяет. В сохранённой записи A остаётся исторически принятой, B содержит новое подтверждение A, а текущее назначение D выбирает это подтверждение. Для этого исхода ожидается код `0`; он подтверждает формальные основания назначения D, а не выполнение самой D.

Остановку с продолжением, местную работу функции и прерванный пересмотр можно сохранить другим генератором:

```sh
recovery_parent="$(mktemp -d)"
python3 -B kit/tests/test_recovery.py --example "$recovery_parent/scenarios"
python3 -B kit/tests/test_recovery.py --feature-example "$recovery_parent/full-feature"
```

Сам `scenarios` должен ещё не существовать. Генератор создаёт в нём `recovery-repo`, `feature-repo` и `r3-repo`, затем печатает JSON с каноническими путями, фактами прекращения процесса, сохранёнными состояниями и исходами диагностики. В `recovery-repo` старая попытка сохранена, существующая правка проверена новой попыткой и принята. `feature-repo` показывает местную сдачу/приёмку и следующее назначение при остановленном общем координаторе без изменения общего источника. `r3-repo` сохраняет частично обновлённый общий пересмотр. Для этих заявленных действий ожидается код `0`; в R3 он разрешает только записанные независимые действия и чтение затронутого поручения.

Вторая команда создаёт другой новый каталог — `full-feature`. Полный сценарий сначала реально проверяет форму существующего JSON и сохранность необязательного поля, затем добавляет заметки и выполняет два теста. Собственный кандидат повторно подтверждает подготовительное обязательство и принимается местно после содержательного разбора кода/рисков. Общий файл в этот период не меняется, общий координатор остановлен. После его возвращения отдельная общая проверка сохраняет несколько книг, добавляет заметку к одной и проверяет её сохранность при следующем добавлении. Только её приёмка закрывает интеграцию; функция передаёт знания, ограничения и сопровождение, освобождая отрезок. В JSON-выводе два намеренных отказа: попытка следующего назначения по непринятому кандидату и подмена общей интеграции местной приёмкой. Сам генератор завершается кодом 0, если все ожидаемые исходы подтверждены. Разбор исходника записан отдельно от автоматических гарантий; дубликаты названий, повреждённые данные и конкурентная запись в учебное требование не входят.

Адресные проверки ниже создают собственные временные данные. Первая группа проверяет реальную остановку до теста, удержание записи при неизвестной судьбе процесса и восстановление R3:

```sh
GIT_OPTIONAL_LOCKS=0 python3 -B kit/tests/test_recovery.py -v RecoveryTests.test_actual_stop_inspect_then_new_attempt_tests_existing_edit RecoveryTests.test_unknown_or_running_paused_cancelled_writer_is_not_released RecoveryTests.test_r3_pending_revision_is_recoverable_and_independent_action_survives
```

Вторая группа проверяет кандидата, который повторно подтверждает принятую зависимость, известный/неизвестный остаток, двойное резервирование и отсутствие двойного счёта через сводку:

```sh
GIT_OPTIONAL_LOCKS=0 python3 -B kit/tests/test_diagnostics.py -v DiagnosticsTests.test_dependent_candidate_rechecks_dependency_before_own_acceptance DiagnosticsTests.test_limits_known_unknown_double_allocation_and_no_double_summary DiagnosticsTests.test_allocations_across_works_share_one_remaining_pool
```

Это адресные команды для разбора поведения. Они не заменяют полный прогон окончательной редакции комплекта.

Отдельный запуск на уже подготовленном учебном состоянии:

```sh
python3 -B kit/tools/kit.py check --root /канонический/путь/к/учебному/repo --state docs/ai-work/state.json
```

Код `0` означает отсутствие найденных формальных противоречий в заявленных действиях; `1` — ошибку данных, связи или чтения; `2` — неподдерживаемую конструкцию. Программа ничего не назначает, не останавливает процессы, не запускает команды из записей и не загружает внешние URL.

## Короткий путь одной задачи

Применяй [порядок короткой работы](../procedures/workflow.md#short-path).

Одна задача не требует функции и отдельной команды. В общем `state.json` есть одна итерация и одна работа со встроенным поручением; профиль хранится отдельным файлом. Один агент совмещает управление, исполнение и приёмку.

Поручение требует нормализовать пробелы в строке и задаёт два проверяемых случая: `'  a   b  '` превращается в `'a b'`, пустая строка остаётся пустой. В `inputs` находятся функция, тест и профиль; разрешена реализация без выпуска. Начальная реализация `value.strip()` не выполняет первое требование полностью.

Агент назначает попытку, выбирает `assign`, затем начинает `execute` и меняет функцию на `' '.join(value.split())`. Сохраняет поручение, попытку и входы в Git до окончательной проверки. После фактического теста сохраняет результат у этой попытки, прекращение процесса и `submitted` с `review`. Затем как принимающий сопоставляет поведение с исходным поручением и добавляет точную приёмку. Следующий `handoff` проверяет применимость выбранного результата.

Отдельный коммит результата и приёмки не меняет функцию, тест и профиль. Поэтому он не требует нового поведенческого теста сам по себе. Выбранный набор входов, содержание поручения и назначенная попытка должны оставаться связанными с проверенной версией. Источник состояния не включают целиком в область входов: его поручение проверяется по содержанию отдельно.

## История A и новое подтверждение B — R1

См. [договор оснований](../formats.md#dependencies).

В воспроизводимом R1 A сохраняет книгу и читает её обратно; C1 — коммит принятой реализации, A1 — результат попытки. B добавляет заметку к книге в том же JSON-хранилище. Проверка B в C2 действительно проверяет сохранение книги и сохранение заметки без потери названия. Одного существования отчёта B для этого недостаточно.

В `checks.covers` результата B перечислены оба обязательства. В таком фрагменте названия иллюстративны; реальные идентификаторы выбирает запись:

```json
[
  {"work": "work-A", "assignment_revision": 1, "criterion": "criterion-A"},
  {"work": "work-B", "assignment_revision": 1, "criterion": "criterion-B"}
]
```

После приёмки B последующая работа D зависит от исторической приёмки A, но выбирает B/C2 как текущее подтверждение `criterion-A`. Её основание содержит точную редакцию результата B, идентификатор проверки и связь с нужным обязательством. В `replacements` остаётся прежняя ссылка A1 с причиной и ответственной ролью. История A1/C1 и её приёмка сохраняются.

При самой приёмке B её собственный кандидат ещё не принят. Если он проверил прежнее обязательство A на изменённых входах, действие `review` B может выбрать эту проверку как текущее подтверждение зависимости A. Кандидат при этом проходит все проверки своего поручения, попытки, входов и покрытия. Такое исключение позволяет принять изменение общего кода без предварительной приёмки самого себя. Отдельное следующее назначение D не может использовать непринятый кандидат B; оно ждёт его приёмки.

Текущая проверка D должна пройти на B/C2 и отказать на одном устаревшем A1, если зарегистрированные входы A изменились. Пустой список оснований, чужой критерий, другая попытка, неверная редакция, отсутствующий источник или проверка без покрытия A не заменяют это подтверждение. Смысл теста B агент разбирает отдельно: он действительно выполняет старый сценарий, а не только содержит слово «совместимо».

Если код изменился только косметически и проверяемое обязательство не затронуто, ответственная роль может обосновать совместимость. Обоснование связано с точными старым/новым коммитами, конкретным обязательством и перечнем существенных различий. При настоящем изменении поведения требуется новая проверка. Новый номер коммита после объединения ветки сам по себе не говорит о новом поведении; сравниваются итоговые входы.

## Остановка после правки до теста и новая попытка

Применяй [восстановление](../procedures/recovery.md#resume).

Учебный исполнитель — отдельный ограниченный процесс. Он меняет `source.py`, не запускает тест и завершается. Родитель действительно ждёт завершения и сохраняет наблюдаемый исход. Код `0` этого процесса относится к записи файла, а не к проверке поведения. Старый PID без такого наблюдения не был бы достаточным основанием.

В файлах остаются исходная попытка с `phase: stopped`, `termination` с фактом завершения, статус работы `paused`, непроверенная правка и `blocker` с шагом «сверить и проверить существующее изменение». Действие `inspect` допускает чтение. Успешный `check` этого этапа не назначает нового исполнителя и не объявляет тест пройденным.

Преемник восстанавливает состояние из сохранённых файлов. Он видит прежнего исполнителя, поручение, правку в Git, отсутствие результата и приёмки и единственное допустимое чтение. После сверки фактов координатор добавляет новую попытку той же работы, сохраняя первую. Назначает единственного владельца записи/Git при необходимости, выбирает `active_attempt` и `assign`. Существующая правка проверяется или исправляется; второй независимый вариант не создаётся.

Перед окончательным тестом новая попытка и входы сохраняются в коммите. После успешной проверки результат относится именно к новой попытке и этому коммиту. Принимающий сопоставляет его с поручением и сохраняет точную приёмку. Это завершает исполняемое продолжение, но не запускает следующую продуктовую работу автоматически.

Если судьба первой попытки неизвестна, сохраняется `unknown`. Ресурс остаётся за ней; второе конфликтующее назначение должно получить отказ. Отмена также не освобождает запись до установленного прекращения исполнения. Поздний ответ первой попытки сохраняется у неё отдельно и не заменяет результат второй. Для зависимости на новую принятую попытку старый ответ не засчитывается автоматически.

Если неизвестен исход внешнего действия, например выпуска, преемник сначала выясняет, доставлена ли версия. Отсутствие ответа не означает, что действие не состоялось. Повтор до выяснения запрещён; настоящий выпуск ради учебной проверки не нужен.

## Функция с местной самостоятельностью

Применяй [мандат и эффекты](../procedures/roles.md#mandate-and-effects) и [право ресурса](../procedures/roles.md#shared-resources).

Первая итерация хранит обычную принятую работу продукта. Для второй появляется отделимая функция — добавление заметок к сохранённым книгам. Общая запись задаёт цель, критерии, договор интерфейса, роль местного координатора, разрешённые этапы и отрезок записи. Она содержит `local_state`, но не копию внутренней очереди.

Местное состояние принимает точную редакцию и Git-содержание общего поручения через `parent`, хранит текущую сессию роли и внутренние работы. Внутри одного общего мандата координатор функции может назначить ограниченный анализ, затем реализацию с тестами, адресный разбор по риску и местную приёмку. Ему не требуется общее одобрение каждого внутреннего назначения. Подготовительный этап `prepare` сам по себе не разрешает реализацию.

Общие `write_owner` и `git_owner` называют функцию как владельца отрезка и изменяющих операций Git. Единственная конкретная местная попытка выполняет эти действия согласно своим `effects`. Общая область и местный исполнитель описывают одно разрешение. Между местными попытками отрезок может оставаться за функцией без изменения общей записи; местный координатор последовательно сдаёт, принимает и назначает работу сам. Ещё одна активная пишущая попытка, старая принятая редакция общего поручения, чужая `active_attempt` или выход за отрезок должны дать отказ.

Общий координатор может быть `stopped`, пока функция продолжает уже разрешённую местную цепочку. В местном состоянии ясны цель, границы, критерии, препятствие и следующий шаг. Прогноз исполнителю не нужен для продолжения. Местная приёмка не превращает функцию в интегрированный продукт: общий координатор отдельно организует работу `kind: integration` и принимает её итоговую редакцию.

Если обе области обнаружили несовместимый общий интерфейс, первичный факт сохраняется для общего координатора и владельца интерфейса. Зависимая запись ждёт единого решения; после исправления проверяются обе стороны на итоговых входах. При закрытии функции сохраняются знания, незакрытые обязательства и владелец сопровождения, прекращаются исполнители и освобождаются запись и расходные назначения. Малое следующее исправление можно оформить обычной задачей продукта.

## Прерванный общий пересмотр — R3

Применяй [пересмотр](../procedures/recovery.md#reassess).

В общей записи сохранено новое решение версии 2. Поручение A уже обновлено, B ещё ссылается на версию 1. В `revision_review` сохранены новая редакция, ответственная общая роль, `updated: ["work-A"]`, `pending: ["work-B"]` и допустимые независимые действия. Координатор остановлен.

Новая сессия восстанавливает тот же пересмотр по файлам. У B статус `revise`, причина — старое общее решение, следующий шаг — согласовать поручение; её действие `inspect`. Разрешённое чтение может пройти с кодом `0`. Если вместо него заявить зависимую реализацию, должен быть ненулевой исход. A тоже не получает права писать только из-за новой ссылки: её собственная готовность, зависимости, местная принятая редакция и единственное право записи проверяются отдельно.

После обновления B общая роль уточняет `updated` и `pending`, а местная при наличии принимает новое поручение. Новое решение пользователя повторно не запрашивается. Отдельная транзакционная система и обязательный новый журнал для этого не нужны.

## Прогресс, повторы и настоящие ограничения

Применяй [порядок прогресса и расходов](../procedures/workflow.md#progress-and-cost).

Предположим, у координатора был справочный прогноз, а доступные наблюдения показывают больше работы. Уже подтверждено сохранение книг, осталось проверить новый сценарий заметок B. Координатор сохраняет этот факт и остаток, устанавливает причину расширившейся проверки, уточняет прогноз при наличии данных и продолжает без нового разрешения. `INFO` о превышении не отклоняет качественный результат.

Другой случай: на неизменённой версии снова выполняют то же ревью, хотя новых замечаний и конкретного сомнения нет. Координатор прекращает лишний цикл и назначает только оставшуюся содержательную проверку или исправление. Разбор задержки не требует ещё одного такого же ревью. При неизвестной паузе активное время не вычисляют, а неизвестные метрики не заменяют нулём.

У настоящего числового ограничения отдельно сохраняются источник разрешения, область и единица. При условном пределе 10 единиц и известном расходе 3 остаток 7 нельзя независимо выделить как 5 и 4: это повторное обещание одного остатка. Если обязательный остаток неизвестен, расходное действие не разрешено, но независимый `inspect` остаётся возможным. Сводка ссылается на первичные расходы попыток и не прибавляет их повторно. Ни покупки, ни платные обращения для этих проверок не требуются.

## Прежние примеры `0.1-p1`

Старые генераторы сохраняются как регрессия ограниченного первого формата. Они создают новые каталоги и не перезаписывают существующие:

```sh
example_parent="$(mktemp -d)"
python3 -B kit/tests/test_kit.py --example "$example_parent/repo"
stopped_parent="$(mktemp -d)"
python3 -B kit/tests/test_kit.py --stopped-example "$stopped_parent/repo"
```

Первый проходит обычную задачу и сохраняет фактические два теста. Второй останавливается после реальной правки до теста и сохраняет прежнюю попытку, наблюдённое завершение и чтение передачи. Для него ожидается **код `2`**, `UNSUPPORTED: task/status`; проверка останавливается на статусе и не подтверждает оставшиеся поля/Git. Это прежний предел `0.1-p1`, а не успешное исполняемое восстановление нового формата.

Для допустимых переходов и сохранения истории открой [договор версий](../formats.md#record-versions). Сведения о прежних проверках — в [справке](../reference/decisions.md#evidence-and-history).
