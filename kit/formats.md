# Договор рабочих записей

Это договор между агентом и `kit.py check`. Агент редактирует JSON; пользователь принимает продуктовые решения в чате. Программа только читает записи и Git. Она проверяет формальные связи. Агент устанавливает достаточность полномочий, полноту входов, правдивость фактов и смысл проверок. Прямое редактирование программа не блокирует.

<a id="record-versions"></a>
## Версии и начальные формы

Сначала установи режим по профилю. В штатном источнике прочитай `format_version` до остальных полей. Поддерживаются только точные значения из таблицы; другие номера не означают автоматически совместимый формат.

| Формат | Допустимое прежнее обозначение | Охват |
| --- | --- | --- |
| [`0.3.0`](#task-format) | — | Карточки в областях, чтение по номеру и адресу материала |
| `0.2.0` | `0.1-p2` | Несколько работ и последовательных итераций |
| `0.1.0` | `0.1-p1` | Одна задача, одна попытка, явные файлы |

Для нового проекта используй карточки `0.3.0`. Для проекта, который ведёт штатный файл состояния, используй его существующий формат. Прежнее обозначение в той же строке означает тот же договор данных; поля не меняются. Диагностика принимает оба обозначения в текущих и исторических записях, а для `0.2.0` — также в смешанных общих и местных областях. Она ничего не переписывает. Существующие записи не переименовывай ради обновления кита; сохраняй историю и точные свидетельства. Ранние программы до выпуска `0.2.0` новых обозначений не понимают. При откате используй [общую процедуру](procedures/adapt.md#update-and-rollback) и проверь совместимость всех используемых записей и исторических входов; обратная замена только текущего номера не гарантирует такой совместимости.

Диагностика `0.1.0` сохраняет прежний ограниченный путь с `implement-and-test`, без непустых зависимостей и лимитов. Остановленный пример сохраняет `paused/stopped` и возвращает код 2 на `task/status`: это не подтверждение остальных полей или поддержка восстановления. Для перехода между двумя разными строками таблицы вручную сохраняют прежние попытки, превращают задачу в элемент `works`, заменяют `write_files` на `write_scope`, `authorized_action` на `stage`, добавляют явные `actions` и список приёмок. Одной замены `format_version` для этого недостаточно. Старые коммиты ограниченного формата не становятся свидетельствами нового: перед новым результатом сохраняют поручение и проверяют входы по нужному договору. Автоматического переноса нет. До переноса читай [порядок смены источника](procedures/adapt.md#partial-and-migration). [Основание совместимости](reference/decisions.md#record-history).

`templates/state.json` и `templates/result.json` относятся к файлу состояния 0.2.0. Первая форма начинает с пустого списка, вторая заполняется только фактическими наблюдениями. Для карточек результат, проверка и решение оформляются по [договору действий](#card-actions). Учебные записи находятся в полной поставке. Версию поставки, формата и редакцию отдельной записи различай по [схеме версий](versioning.md).

<a id="state-and-history"></a>
## Состояние, источники и история

Все перечисленные поля обязательны, кроме явно необязательных. Неизвестные поля/версии не игнорируются. Повтор JSON-ключа, идентификатора, строки в списке или действующего локального источника — ошибка. Идентификаторы состояния, решения, итерации, работы, поручения, критерия, попытки, результата, проверки, приёмки и ограничения уникальны во всех загруженных областях. Вид ссылки определяется полем. ID начинается латинской буквой, далее допустимы буквы, цифры, `.`, `_`, `-`. Имена ролей и сессий не являются ID записей.

Редакция — положительное целое число; `true` и `1.0` не заменяют `1`. Изменение смысла поручения повышает его редакцию. Исправление представленного результата повышает редакцию результата. Статус сам не меняет поручение. Состояние повышает `revision` после содержательного обновления, чтобы сводки могли установить прочитанную редакцию. Git хранит историю; программа не доказывает всю последовательность переходов.

`assignment` и `attempt.result` содержат либо сам объект, либо только `{"path":"относительный/файл.json"}`. Требование/результат хранится один раз. Локальный внешний JSON проверяется так же, как встроенный. Повтор одного файла как двух живых записей запрещён. Внешнее `{"url":"https://…"}` явно непроверено и даёт код 2 для обязательного источника. Необязательный `external_links` даёт информационные сообщения; URL не загружаются и не заменяют обязательное свидетельство.

Markdown хранит профиль, нормативные решения и пояснения; произвольный смысл Markdown программа не понимает. Развёрнутое поручение штатного машинного формата — внешний JSON. Markdown может его пояснять, но не дублировать живые требования/статусы. Подключение к чужому формату определяется в [процедуре применения](procedures/adapt.md); сопоставление статусов не меняет программный формат.

### Общее и местное состояния

Короткий путь описан в [рабочем порядке](procedures/workflow.md#short-path).

Таблица показывает поля состояния.

| Поле | Смысл |
| --- | --- |
| `format_version` | `0.2.0`; прежнее обозначение — по таблице версий |
| `id`, `revision` | Уникальная область учёта и её редакция |
| `scope` | `product` у файла входа; `feature` у местного файла |
| `profile` | Путь к существующему Markdown-профилю продукта |
| `editor` | `role`, `session`, `status` (`active`/`stopped`): единственный редактор, текущая сессия логической роли, состояние сессии |
| `iterations` | Непустой список `id`, `goal`, `status`: `planned`, `active`, `integrated`, `released` |
| `works` | Принадлежащие области работы; список может быть пустым при подготовке |
| `continuation` | `owner`, `last_completed`, `unverified` (список), `next_step`: достаточная передача из файлов |
| `actions` | Необязательный список текущих действий; правила ниже |
| `parent` | Только местно: `work`, `assignment_revision`, `commit` — общее поручение функции и полный коммит принятого местной ролью содержания |
| `write_owner`, `git_owner` | Только общая область, необязательны/`null` без выделенного отрезка. Оба обозначают область: ID продукта либо активной работы-функции. Конкретный писатель и исполнитель изменяющих Git-операций определяются её единственной местной попыткой |
| `decisions` | Только общая область, необязательный список `id`, `revision`, `source` (нормативный файл) |
| `revision_review` | Необязательная точка общего пересмотра R3 |
| `forecast` | Необязательный прогноз; внутри обязателен `estimate`, необязательны `observed` (число/`null`), `unit`, `analysis` |
| `real_limits`, `usage_views`, `external_links` | Необязательные ограничения, ссылки на первичные расходы и URL |

У итерации `integrated`/`released` обязателен `integration`: приёмка работы вида `integration` в этой же области/итерации. `released` требует также `release` — сохранённый факт доставки. Правдивость факта проверяет агент. Местная приёмка функции не закрывает общую интеграцию.

Общий реестр хранит работу-функцию и `local_state`, а не копию её очереди. Сессия функции меняется только местно; общее поручение назначает логическую роль. При местном продолжении `parent` совпадает с нынешней редакцией и содержанием общего поручения. Различие только номера HEAD не мешает, если принятое содержание то же. Чтение устаревшей области помогает выяснить остаток, но не разрешает реализацию.

<a id="assignment-and-inputs"></a>
## Работа, поручение и входы

Работа содержит `id`, `kind` (`task`, `question`, `feature`, `integration`), `iteration` (местная итерация), `status`. У `candidate` есть только эти поля и непустая `idea`: идея ещё не назначение. Остальные состояния имеют `assignment`; необязательны `attempts`, `active_attempt`, `acceptances`, `current_acceptance`, `blocker`. Только функция имеет `local_state`, необязательные `view` и `closure`.

Поля поручения показаны ниже.

| Поле | Смысл |
| --- | --- |
| `id`, `revision`, `goal`, `boundaries` | Точная норма и границы результата |
| `inputs` | Непустой список файлов/папок существенных входов, в пределах [поддерживаемых путей](#paths-and-git) |
| `write_scope` | Разрешённые файлы/папки кода, тестов, сборок и общего ресурса, внутри `inputs`; для анализа допустим `[]` |
| `criteria` | Непустой список `id`, `expectation`: наблюдаемые критерии |
| `plan` | Непустой список действий подходящей глубины |
| `acceptor` | `editor.role` этой области; роли могут совмещаться |
| `stage` | `prepare` — чтение/подготовка; `implement` — реализация внутри выданной области |
| `authority` | `by`, `source`: происхождение разрешения, существующий нормативный файл |
| `dependencies` | Необязательные `work`, `acceptance`, `criterion`; `acceptance:null` допустима для будущей незапущенной работы |
| `decisions` | Необязательные `id`, `revision` общих решений |
| `mandate` | Только функция: `role`, `stages` (из `prepare`/`implement`), `interfaces`, `closing` — местные полномочия и условие закрытия |

Местные этапы не расширяют общее разрешение: при общем `stage:prepare` в `mandate.stages` допустим только `prepare`. Общий `implement` может разрешать местную подготовку и реализацию. Противоречивые поля отклоняются, а не трактуются как дополнительное разрешение.

Профиль, источник разрешения и выбранные общие решения входят в `inputs`. Файлы состояния туда не входят: содержание поручения проверяется отдельно от статусов. Полноту входов выбирает агент. Папка включает сохранённые файлы и новые неигнорируемые файлы, поэтому устаревший перечень не скрывает добавление внутри области. Секреты, новые игнорируемые данные и неизвестная внешняя среда не объявляются проверенными по Git. Внешние JSON-поручения сравниваются по сохранённому содержанию, а не только по номеру редакции.

<a id="attempts-and-actions"></a>
## Попытки, состояния и действия

Попытка содержит `id`, `assignment_revision`, `executor`, `phase`, `effects`. Фаза: `assigned`, `running`, `unknown`, `stopped`, `finished`. `effects` — непустой набор из `read`, `write`, `git`, `external`. `write` включает изменяющие общую папку тесты/генераторы. Применимые правила этапа и записи своей памяти определяет [мандат роли](procedures/roles.md#mandate-and-effects). Диагностика проверяет сочетание `prepare` с эффектами при назначении, исполнении, приёмке, передаче и выборе результата текущим основанием. Невыбранная история остаётся читаемой.

Для `stopped`/`finished` обязателен `termination:{by,fact}` с фактическим основанием; у остальных его нет. При `external` обязателен `external_outcome`: `unknown`, `confirmed`, `not-performed`. Неизвестный внешний исход выясняют до повторения действия.

Непрекращённая попытка принадлежит `active_attempt`. Для диагностики активны фазы `assigned`, `running`, `unknown`; программа считает активные попытки с `write` или `git` и проверяет, что их не больше одной и что область совпадает с `write_owner`. `git_owner`, если указан, совпадает с `write_owner`. Любая активная попытка с `git` требует `git_owner` своей области. Для передачи действуют [правило ресурсов](procedures/roles.md#shared-resources) и [фактическая остановка](procedures/recovery.md#resume). Программа проверяет запись факта, но не удостоверяет остановку процесса. Для новой попытки запиши новый ID, сохрани прежние попытки и результаты.

Таблица связывает статус поручения с заявленным действием.

| Статус | Смысл |
| --- | --- |
| `ready` | Текущая `assigned` попытка; обязателен `assign` |
| `in_progress` | Текущая `running` попытка; обязателен `execute` |
| `submitted` | `finished` попытка с результатом; обязателен `review`, кандидат ещё не принят |
| `accepted` | `current_acceptance` выбирает приёмку текущей попытки и того же содержания поручения; исторические входы не обязаны быть нынешними |
| `blocked`, `paused`, `cancelled`, `revise` | Обязателен `blocker:{reason,next_step}`; допустим только `inspect`. Непрекращённая старая попытка может удерживать ресурс |
| `candidate` | Намеченная идея; допустимо чтение |

Для общей попытки координации функции и местных попыток применяй [правила мандата](procedures/roles.md#mandate-and-effects). Требование эффекта общей попытки агент сверяет отдельно. После общей приёмки функции обязательна `closure:{knowledge,obligations,owner}`: знания, открытые обязательства и владелец сопровождения. Местные исполнители прекращены, назначения ресурса освобождены. Малое последующее исправление можно вести обычной задачей.

Действие относится к работе в своём источнике: `work`, `kind`. Пара работы и вида действия уникальна. У `inspect` других полей нет: это только чтение/разбор. Остальные действия обязательно содержат `bases`, даже если независимой задаче достаточно `[]`.

`assign`, `execute`, `review` соответствуют таблице статусов. `handoff` выбирает принятый результат как актуальное основание передачи. Заблокированную работу передают через `inspect`, `blocker` и конкретный шаг `continuation`, без выдуманной готовности писать. `spend` проверяет отдельную расходную операцию и сам не разрешает запуск кода/внешнего действия.

<a id="results-and-acceptance"></a>
## Результат и историческая приёмка

Результат может сохраняться у исторической `stopped` или `finished` попытки. Для текущего кандидата действует таблица попыток и статусов. `attempt.result` пишет исполнитель, встроенно либо во внешнем локальном JSON. Поля: `id`, `revision`, `assignment_id`, `assignment_revision`, `attempt_id`, `executor`, `summary`, `commit`, `artifacts`, `checks`, `unverified`, `limitations`, `next_step`. Списки `unverified`, `limitations` могут быть пустыми; `next_step` — строка. `commit` — полный существующий коммит с поручением, назначением попытки и входами. `artifacts` — непустой список предъявленных файлов/папок из входов, сохранённых в коммите.

Проверка содержит `id`, `covers`, `command`, `cwd`, `expected`, `observed`, `outcome` (`passed`/`failed`), `environment`. `cwd` — безопасный относительный путь к папке проверки; `.` допустима. Исторический каталог проверяется по дереву сохранённого коммита и не обязан существовать сейчас. У собственного текущего кандидата `review`/`handoff` каталог должен существовать и сейчас. Пустой неотслеживаемый каталог не подтверждается историей Git: используйте сохранённую рабочую папку и отдельно опишите внешнюю среду. `covers` — непустой список точных обязательств `work`, `assignment_revision`, `criterion`. Проверка может покрыть чужое обязательство, если оно действительно проверялось. Смысл покрытия оценивает принимающий. **Порог представления и приёмки.** У всех собственных обязательных критериев точного кандидата должны быть успешные, применимые свидетельства с точным покрытием. Непроверенный критерий, недоступное обязательное свидетельство и неуспех не проходят порог. Старый неуспех сохраняется в отдельной попытке. Команда из записи не исполняется диагностикой.

Приёмки находятся в `work.acceptances`. Поля: `id`, `result`, `result_revision`, `assignment_revision`, `by`, `evidence`, `unresolved`, `applicability`. `evidence` выбирает успешные проверки данного результата и покрывает его собственные критерии. `by` равен принимающему в сохранённом поручении. `current_acceptance` существует только при `accepted`, выбирает результат `active_attempt` и то же содержание нынешнего поручения. Поздний ответ не заменяет новую приёмку. Исторические приёмки остаются при новом назначении без `current_acceptance`.

Для истории поручение, назначение и наличие обычного файла `authority.source` проверяются по коммиту результата. Исторический источник разрешения не обязан существовать сейчас, если результат не выбран текущим основанием. Путь всё равно проходит проверку границ и ссылок; действующий профиль каждой области обязателен. Текущее действие требует нынешний источник своего разрешения. Для собственного кандидата `review`/`handoff` дополнительно сравниваются поручение в нынешнем файле, HEAD, индексе и свежесть входов. Исключение для свидетельства уже принятой зависимости см. в [основаниях](#dependencies).

<a id="dependencies"></a>
## Текущие основания зависимостей

Для каждой зависимости нужен ровно один объект `bases`: `work`, `acceptance`, `criterion`, `result`, `result_revision`, `check`. Приёмка относится к нужной зависимости, которая остаётся принятой на выбранной приёмке. Текущее подтверждение может принадлежать другой работе, но его выбранная успешная проверка явно покрывает нужное обязательство и принята. Содержание поручения обязательства в коммите нового подтверждения должно точно совпадать с поручением из исходной приёмки: совпадения ID и номера недостаточно. Поручение обязательства строго сравнивается с рабочей записью, HEAD и индексом. Собственное историческое поручение выбранного подтверждения сравнивается отдельно с каждой из этих трёх версий, если та сохраняет ту же пару `assignment.id` + `revision`: подмена содержания при прежней паре запрещена. Законное новое поручение работы-подтверждения не заменяет её прежний принятый результат и не обесценивает подтверждение неизменного обязательства на тех же входах. Новая рабочая редакция не скрывает подмену старой редакции в HEAD или индексе. Собственный текущий кандидат по-прежнему сверяется строго. Сравниваются нормативные поля, а не весь реестр; старые приёмки не переписываются. Исключение — только `review` собственного текущего кандидата: его проверка может заново подтвердить и обязательство принятой зависимости после своей правки. Сам кандидат проходит все проверки поручения/входов, но не обязан принять себя заранее. Для отдельной следующей работы непринятый кандидат основанием не служит. Пустой список не заменяет зависимость. Неизвестные работы, критерии, ссылки на несуществующую ненулевую приёмку и циклы запрещены. Будущая зависимость с `acceptance:null` сама не запрещает независимое действие, но не разрешает зависимое.

В R1 A принята по A1 в C1. B меняет общий код и в C2 проверяет также обязательство A. Следующая работа хранит зависимость от приёмки A, а подтверждение выбирает B1/C2. A1 остаётся историей C1 и не блокирует C2. Если старое разрешение A архивировано, новое B может подтвердить точное поручение A на собственных действующих входах/разрешении. Входы A не становятся входами B автоматически. Выбор самого A1, напротив, требует актуальности всех его входов, включая источник разрешения; совместимость не заменяет отсутствующий источник и не разрешает иной текст обязательства. Выбор одного A1 при изменённых значимых входах не проходит.

При смене результата подтверждения обязателен непустой `replacements`. Каждый элемент хранит прежние `result`, `revision`, `check`, `reason`, `by`; первый относится к исходной приёмке зависимости. Прежние источники и связь обязательства сохраняются. Обоснованность замены проверяет агент.

Для незатрагивающей обязательство правки допустимо `compatibility` в основании: `from_commit`, `to_commit`, `work`, `assignment_revision`, `criterion`, `differences`, `reason`, `by`. Пара коммитов точная; `differences` перечисляет ровно изменённые входы выбранного свидетельства, список непустой. Новая сторона совпадает с нынешними входами. Надпись «совместимо» не является доказательством. Программа проверяет привязку, агент — отсутствие влияния. Изменившееся поведение требует новой проверки.

<a id="paths-and-git"></a>
## Пути, Git и существенные входы

`--root` — канонический корень обычного локального Git-репозитория, без символической ссылки в нём/родителях. Пути нормализованы и относительны ему; запрещены `..`, `.git`, обратная косая черта, двоеточие, переводы строки/NUL. Ссылки запрещены во всех компонентах и внутри зарегистрированных папок. Данные не задают дополнительный корень. Каждый отдельный путь `inputs` должен существовать при проверке текущего действия, кроме `inspect`. Весь корень (`.`) запрещён во входах. Артефакт подтверждается в сохранённом коммите. Новый файл опиши в поручении и покрой существующей папкой входов. Его будущий путь может быть в `write_scope` внутри этой папки. Если такой области нет, сначала согласуй создание допустимой основы. Состояние исключено из списка существенных входов. Точка `.` допустима для `cwd` проверки. Это доверенная локальная папка без одновременной подмены путей; защита от враждебной гонки не заявлена.

Сначала сохраняют входы/поручение в Git, потом проверяют, затем записывают результат с номером существующего коммита. Коммит не ссылается на самого себя. Отчёт можно сохранить следующим коммитом. У выбранного текущего результата сравниваются набор входов, содержание и права исполнения в проверенном коммите, нынешнем HEAD, индексе и рабочем дереве. Новые неигнорируемые файлы внутри области обнаруживаются. Сравниваются исходные рабочие байты, а не вывод о чистоте после Git-преобразования. Например, Git может считать файл с преобразованными окончаниями строк чистым, а диагностика отклонит отличие. Для выяснения используй [безопасный осмотр](procedures/adapt.md#git-inspection). Обязательное неподтверждённое условие остаётся открытым до установления поддерживаемой редакции. Различие SHA после объединения само не является изменением поведения: одинаковые итоговые входы допускают прежнее свидетельство.

<a id="diagnostics"></a>
## Диагностика

Для штатного локального Git-репозитория нужны Python 3 и [рабочая часть](procedures/adapt.md#placement). Из канонического корня при типовом размещении:

```sh
GIT_OPTIONAL_LOCKS=0 python3 -B .ai-kit/tools/kit.py check --root "$PWD" --profile docs/ai-work/project.md
```

Для клона используй `.ai-dev-kit/kit/tools/kit.py`. Из вложенной папки подставь фактический путь к программе и полный канонический корень. Для явной проверки прежнего файла используй `check --root "$PWD" --state docs/ai-work/state.json` с его фактическим путём. Моменты проверки определяет [рабочий порядок](procedures/workflow.md#diagnostic-transitions). Для чужого режима действуют [проверки агента](procedures/adapt.md#partial-and-migration). Для особого основания изготовления или установки прочитай [условия снимков](procedures/adapt.md#install-check).

Чтение использует `GIT_OPTIONAL_LOCKS=0`, очищенное от внедрённых `GIT_*` окружение, отключённые глобальную/системную конфигурации, hooks, fsmonitor, сеть, lazy fetch и замены объектов. Конфигурация сначала разбирается отдельным Git без обнаружения репозитория: `--git-dir=/dev/null`, `--no-includes`, переданные байты. Запрещены действующие ключи `include.*`, `includeIf.*`, `extensions.*`, `worktree.*`, `core.worktree`, `remote.*.promisor`, `remote.*.partialCloneFilter`. Безвредные слова в значениях/комментариях не дают отказа. Gitfile, worktree, внешние объекты, alternates/grafts и служебные ссылки не поддерживаются. При поиске новых входов внешний `core.excludesFile` переопределяется `/dev/null`; используются локальные `.gitignore` и `.git/info/exclude`. Обработчики diff/textconv, фильтры и команды из данных не запускаются.

Коды: `0` — формальных противоречий в заявленных действиях не найдено; `1` — неверные данные/несогласованность/ошибка чтения; `2` — неподдерживаемая версия, конструкция или неверные аргументы команды. Сообщается первая проблема с адресом записи. Русский Unicode сохраняется; непечатаемые в текущем потоке символы экранируются. INFO сообщает об ограничениях или наблюдениях без отказа. При успехе `inspect` проверен только разбор. Успех не выдаёт полномочия, не подтверждает качество продукта, всю историю, остановку или соблюдение текстовых условий роли. Действующий специальный мандат и роль редактора агент сверяет по [правилам ролей](procedures/roles.md#mandate-and-effects). Код 1 или 2 для обязательного условия оставляет его непроверенным.

<a id="coordination-records"></a>
## Записи координации и общего пересмотра

Поля общего поручения функции, местного состояния и завершения определены в [поручении](#assignment-and-inputs), [состоянии](#state-and-history) и [попытках](#attempts-and-actions). Перед использованием мандата открой [правило ролей](procedures/roles.md#mandate-and-effects). Одного уровня местного состояния достаточно для поддерживаемого формата: вложенная функция не поддерживается. Если сохранена необязательная `view`, диагностируется её точная ссылка и прочитанная редакция. Для местного действия кроме `inspect` общая работа должна быть `ready` или `in_progress`. Диагностика сверяет принятую редакцию и содержание общего поручения из `parent.commit` с действующей записью, а существенные нормативные входы (общий профиль, источник разрешения и выбранные решения) — в `parent.commit`, нынешнем HEAD, индексе и рабочих файлах. Просроченная сводка даёт отказ общего состояния.

`revision_review` содержит `decision`, `revision`, `owner`, `pending`, `updated`, `independent_actions`. Сначала сохраняют новое решение и остаток, затем обновляют поручения. `pending` точно перечисляет непринятые работы, ещё ссылающиеся на старую редакцию; `updated` — уже согласованные непринятые работы. Исторические принятые поручения не переписываются ради нового решения. Ответственный — редактор общей области. `independent_actions` объясняет допустимые действия, но машинные разрешения остаются в `actions`.

Порядок продолжения — [пересмотр](procedures/recovery.md#reassess).

<a id="cost-records"></a>
## Записи прогноза и ограничений

Сопоставимые неотрицательные конечные числа прогноза могут дать INFO о превышении без отказа или смены статуса. Отсутствие или `null` наблюдения означает неизвестное. До расходного действия применяй [порядок работы с ограничениями](procedures/workflow.md#progress-and-cost).

`real_limits` хранится только в общей области. Каждое ограничение содержит `id`, `source:{by,path}`, `scope` (работы, включая внутренние работы выбранной функции), `unit`, `cap`, `remaining`, `usage`, `allocations`. Источник разрешения существует локально. Числа в одной указанной единице неотрицательны и конечны. Дробные JSON-числа, включая экспоненциальную запись, читаются непосредственно как точные десятичные значения, без промежуточного двоичного `float`; суммы и сравнения ограничений выполняются рациональной арифметикой. Это единая политика для `cap`, `remaining`, `usage.amount`, `allocations.amount` и `spend.amount`. Например, расход `9007199254740993.0` превышает предел `9007199254740992`; формы `0.2`, `0.20` и `2e-1` обозначают одну величину. Отрицательные, неконечные, булевы и строковые значения не являются допустимыми суммами. Целые редакции по-прежнему требуют целый JSON-тип: `true` и `1.0` не заменяют редакцию `1`. Предела 53-битной точности нет; действуют ресурсы локального Python, а не обещание обработки чисел произвольного размера. `usage` — первичные записи `attempt`, `amount` (число/`null`), каждая попытка один раз в данном ограничении. Известная сумма не превышает `cap`. Известный `remaining` равен `cap` минус сумма; при неизвестном расходе остаток не объявляют известным.

`allocations` содержит `work`, `amount`: это распределение остатка, а не новые расходы. Одна работа не резервируется повторно; общая сумма не превышает известный остаток. Закрытая функция освобождает и прямое распределение, и распределения её внутренних работ. Ненулевое оставшееся назначение даёт отказ; нулевое допустимо. Редактор явно удаляет/обнуляет резерв и только затем распределяет освобождённый остаток другой работе. Программа сама не правит записи. Первичные расходы и ссылки `usage_views` сохраняются; принятие внутренней задачи активной функции само по себе резерв не освобождает. `usage_views` содержит только `limit`, `attempts`: ссылки на первичные расходы без добавляемой суммы. Поэтому сводка не прибавляет расход второй раз. Это проверка подготовленных чисел, не интегратор денег или квоты.

Действие `spend` дополнительно требует `limit`, `amount`, известный обязательный остаток и достаточное назначение этой работе. Неизвестный остаток запрещает соответствующий расход, а не независимое чтение/работу без него. Настоящие запреты, включая запрет покупать новые средства, исполняет агент; технического финансового барьера нет. Покупки и исследовательский опыт этими записями не разрешаются.

<a id="task-format"></a>
## Карточки и области формата 0.3.0

`0.3.0` — новый договор данных по [схеме версий](versioning.md#record-version).
Карточка содержит свой `format_version`. Номер поставки комплекта и целая
редакция поручения сохраняют собственный смысл.

**Выбор источника.** Из действующего входа возьми путь заполненного профиля
от корня проекта. `check --root . --profile ПУТЬ` читает одну отдельную строку
`<!-- ai-kit:task-source {"format_version":"0.3.0","path":"docs/tasks"} -->`
(сырой текст Markdown, без кавычек вокруг комментария). В профиле допускается
ровно одна такая строка. `path` — каталог внутри корня, с произвольным
размещением. Отсутствующая, повторная, сломанная или неизвестная запись
приводит к отказу. Для файла состояния в этой строке можно указать его
поддерживаемый формат и путь к файлу. Фактическая версия должна совпасть с
объявленной с учётом старых обозначений. Явный `--state ПУТЬ` читает прежний
файл состояния. Старый вызов без обоих аргументов читает
`docs/ai-work/state.json`. `--state` и `--profile` взаимоисключающие.

Обычный `check --profile` показывает выбранный источник и точку
продолжения по записи каждой области. Если в её карточке есть
`waiting.next_step`, команда и браузер выводят этот текст. Для проверки
права в определённой редакции используй [адресное действие](#card-actions).

**Области.** Выбранный каталог — общая область `P`, а его непосредственные
каталоги `features/F-имя` — области функций. Каждая содержит свою
[запись области](templates/scope.md) `scope.md` с единственным редактором,
ролью и сессией, точкой продолжения, допустимой записью и основанием полномочий.
Каталоги `open`, `done` и `closed` содержат папки задач. Пустой каталог
допустимо опустить, поскольку Git его не хранит. Имя папки — местный номер вида
`T-008` с тремя или более цифрами и необязательным суффиксом из строчной
латиницы, цифр и дефисов. `task.json` содержит тот же местный номер. Полный
номер (например, `F-search/T-008`) образуется из области и номера карточки.
Номер выдаёт редактор, он остаётся за работой при переносе, отмене и закрытии.
Путь карточки определяется размещением. Связь вложенности хранит ребёнок,
через один необязательный `parent` с полным номером. Связь результата хранит
потребитель в `dependencies` с полями `task`, `criterion` и `acceptance`.
`acceptance: null` отмечает ожидаемое основание; непустой ключ указывает
на конкретное именованное решение о приёмке, из которого берётся редакция.

Точка продолжения принадлежит записи области. Общую запись о выдаче ресурсов
ведёт один владелец, назначенный координатором продукта. Укажи её адрес в
области, например `docs/tasks/resources.md`, а в самой записи сохраняй
держателя, ссылку на запуск и границы выданного права. Права записи исполнителя
задаются поручением и фактической выдачей ресурса. Координатор редактирует
карточку, выделенному исполнителю принадлежит только разрешённая часть
продукта и его выделенный файл результата. При необходимости раздельные
план, отчёт, заключение и основания держат рядом, а карточка указывает,
где читать их точную редакцию. Между последовательными назначениями в рамках
действующего мандата следующий запуск ждёт установленного прекращения
предыдущего. Общий читатель проверяет наличие `scope.md`. Для проверки
конкретного перехода используются структурированные записи ниже.

**Содержание `task.json`.** Для идеи достаточно `format_version`, `id`,
`title` и `goal`. Для исполнения добавь блок `assignment`: положительная
целая `revision`, `description` (текст или `{"path":"description.md"}`),
`boundaries`, `write_scope` с разрешёнными путями от корня (пустой список
для чтения), `authority` с `by` и `source`, роль `acceptor` и непустой
список наблюдаемых `criteria` с местными ключами `id` и условиями
`expectation`. Краткий план можно записать как `assignment.plan`.
Длинное описание находится в указанном соседнем файле. Критерии всегда
остаются в карточке. При существенном изменении сохраняй предыдущее поручение
и основание новой редакции. При ожидании добавь `waiting` с тремя строками
`remaining`, `reason` и `next_step`. У ранее учтённой работы `origin`
сохраняет исходную отметку `status` и её `source`.

**Наблюдения и решения.** Каждый элемент `observations` содержит местный
`id`, автора `by`, дату `date`, редакцию поручения `revision`, ключи
проверенных `criteria`, фактическое наблюдение `fact` и `source`.
В `source` укажи происхождение в тексте (например, сообщение пользователя
с датой) либо один точный адрес материала по договору ниже. Если отчёт
принадлежит отдельному исполнителю, в карточке достаточно кратко обозначить
относящийся к критерию факт и сослаться на сохранённый отчёт. Решения
`decisions` идут от раннего к последнему. Каждое содержит `outcome`,
автора `by`, роль `role`, дату `date` и `reason`. Сохранённое основание
при необходимости указывается через `source`. Для `accepted` нужны
`revision` и ключи `observations` той же редакции. Последняя успешная
приёмка должна покрывать все критерии текущей редакции и быть записана в
принимающей роли. Для передачи приёмки по прямым наблюдениям нужен сохранённый
снимок проверенной версии. Если приёмку выбирает другая работа, присвой ей неизменный
`id`. При `replaced` укажи полный номер `replacement`; также допустимы
`rejected`, `cancelled`, `revoked` и `reopened`. У отзыва `revokes` указывает
ID предыдущей приёмки, которую отозвала принимающая роль. Прошлая дата
восстанавливается по решению в исторической карточке этой задачи. При наличии
только наблюдения принимающий может принять результат сегодняшней датой
после фактической проверки. Если
проверить критерий пока нечем, сохрани `origin` и открытый остаток.

Перед переходом по карточке и переименованием сверяются решения из рабочей
карточки, индекса и последнего коммита. Адрес определяется по номеру отдельно
в каждом слое. Рабочая история сохраняет порядок и ранее записанные поля
каждого сохранённого решения. Можно добавить новый факт решения, а к прежней
записи добавить недостающий ID, адрес основания или источник с обычной
проверкой их применимости. При расхождении восстанови сохранённую историю
и вместе с принимающей ролью установи, какое решение действует. Первая
приёмка может быть записана только в рабочем файле. После отзыва для
переноса в `done` требуется новая обоснованная приёмка.

**Решение и размещение.** Ожидаемая папка задаётся последним решением.
`accepted` ведёт в `done`. Отказ, отмена и замена ведут в `closed`
после разрешения ожидания. Идея, работа без финального решения и повторно
открытая карточка ожидаются в `open`. Читатель показывает фактическую и
ожидаемую папку. Расхождение между `open` и ожидаемой папкой сообщает о
незавершённом переносе. Для записи редактор использует отдельную команду
[`move`](#move-review). Дубль полного номера
запрещён, даже если байты совпадают. Отсутствующий родитель, второй родитель,
отсутствующие задача, обязательство или выбранная приёмка и циклы отдельно
диагностируются. Архивная цель остаётся доступна; если выбранное решение
потеряло силу или размещение не завершено, читатель указывает проверить
применимость. Решения о закрытии без выполнения сохраняют `open`, пока есть
ожидание или не установлен исход удерживающей попытки. Структурная проверка
подтверждает связи записей. Достаточность фактического наблюдения устанавливает
принимающая роль.

<a id="card-actions"></a>
### Проверка действия по карточке

Из корня проекта вызови `check --root . --profile ПРОФИЛЬ --task P/T-008 --action ДЕЙСТВИЕ --actor СЕССИЯ`.
Для назначенной работы укажи `--attempt ID`. Действия — `assign` перед выдачей
управления, `execute` перед исполнением, `review` перед приёмкой и `handoff`
для проверки принятого результата перед передачей. В `execute` значение
`--actor` — исполнитель; в остальных переходах — сессия редактора. Эти значения
сверяются с записями. Среда и участники отвечают за подлинность полномочий.
Прежний `check` без `--action` читает структуру и ссылки всех карточек, а
для явно сохранённых прежних редакций и восстановленных решений также сверяет
адреса в истории. Команда читает файлы и Git. Изменения записывает их редактор.

**Область и выдача.** Используй одну машиночитаемую строку
`<!-- ai-kit:scope {...} -->` в `scope.md`. Её поля показаны в [форме области](templates/scope.md).
В общей области `resources` ведёт к JSON с полями `editor` и `grants`.
Редактор выдачи хранит одну запись на ресурс. У каждого элемента есть
`resource`, `holder` (номер области), `work` (полный номер общего поручения)
и `revision`. Выдача области `P` добавляет `attempt` с ID конкретного запуска
этой работы. Выдача функции указывает на её общий мандат. В мандате
`assignment.mandate` указывает `scope` и `role`; в местном `scope.md`
`mandate` содержит `task` и `basis` (Git-адрес принятого поручения).
Поле `assignment.mandate.stages` перечисляет конкретные местные этапы
`prepare` и/или `implement`. Общий этап `prepare` допускает только местную
подготовку. Общий этап `implement` может предоставлять местной роли только
подготовку. В уже существующей карточке без `stages` действует прежнее
правило общего этапа. При переносе сохраняется явный список старого мандата.
Изменение списка требует нового сохранённого решения общей роли и принятого
снимка мандата в области функции.
В местной карточке укажи затрагиваемый продуктовый отрезок в `write_scope`,
в том числе когда правку сделал пользователь. Приёмка и передача проходят
в пределах отрезка общего мандата. Право начать запись выдаётся тому, кто
будет её выполнять.

**Снимок поручения.** До запуска сохрани карточку в Git. В снимок входят цель,
блок `assignment`, зависимости и соседний `description.md`, если он задан.
`assignment.stage` задаёт `prepare` или `implement` (по умолчанию
`implement`; в мандате этап явный). `assignment.inputs` перечисляет
существенные файлы от корня, которые должны сохранять байты для действия,
включая влияющие действующие правила и источники разрешения, если действие
зависит от их текущего текста. Меняемые результаты перечисляются в
отчёте и при необходимости в `result.artifacts`. `assignment.resources`
перечисляет отдельно разрешённые `git` и `external:цель`.
Непустой `write_scope` задаёт право `write` в перечисленных путях.
`write` и `git` относятся ко всему общему рабочему дереву и индексу соответственно.
Для `prepare` права на эти ресурсы отсутствуют. Сверка сопоставляет поручение и
выбранный источник профиля, значащие файлы в сохранённом снимке, `HEAD`,
индексе и рабочих байтах. Соседние файлы вне заявленных оснований не участвуют.

**Попытка.** В `attempts` редактор сохраняет `id`, `executor`, `revision`,
`basis` (исторический адрес карточки с `commit` и `path`), `phase` и
`resources` (реально используемые права). `proposed` ожидает назначения.
Перед передачей управления сохрани запись с исполнителем и ресурсами в Git,
а в `launch` укажи адрес этого снимка. Сверка действия сравнивает
назначение с этим снимком.
`assigned`, `running` и `unknown` удерживают ресурсы. В `finished` и
`stopped` необходимо `termination` с `by` и `source`. Перед конфликтующим
действием сверяются ресурсы прежнего запуска в его сохранённом назначении
и в текущих записях, включая индекс и последний коммит. Если подтверждение
прекращения дано адресом материала, материал должен читаться по этому адресу.
Если в Git есть выданная попытка, а рабочая карточка показывает только прежнее
предложение или не содержит этой попытки, восстанови запись и установи её исход.
Фактическое подтверждение прекращения устанавливает ответственная роль.
Сохрани результат
исходной попытки в `result` с `outcome` (`submitted` или `failed`),
`source` (Git-адрес отчёта) и при необходимости `artifacts` (пути
проверенных результатов в том коммите). Внешняя операция хранит один
`external:цель` и `external_outcome` (`pending`, `unknown`, `done`
или `not-done`). Даже после прекращения процесса `unknown` удерживает
внешний ресурс. Сведения о позднем ответе добавляются к исходной попытке,
в том числе через наблюдение с её ID.

**Приёмка и история.** Для решения по отдельной сдаче укажи `attempt`.
Наблюдения с указанным запуском должны относиться к той же попытке и редакции.
Для решения по самостоятельному наблюдению укажи `basis` с `commit` и
`path` исторической карточки в проверенной редакции. В этом коммите должны
быть проверенные существенные входы и текст поручения, включая отдельное
описание. Выбирай снимок по факту проверки. Его байты сверяются с рабочими
файлами, индексом и последним коммитом при передаче. Прямую приёмку ведут
без `attempt`, в том числе после подтверждённо завершившейся неуспешной
попытки. Удержание ресурса и неизвестный внешний исход по этой задаче
требуют разрешения до приёмки. Прежние решения без сохранённого снимка
остаются читаемыми. Передача и использование как основания требуют
установить проверенную версию или принять по новой проверке.

В приёмке местной области укажи применённый общий `mandate` по форме из её
`scope.md`, с полным номером общей задачи и историческим адресом поручения.
При передаче он должен совпадать с действующим мандатом. Сохрани решение
в Git, пока мандат действует. Для зависимой работы выбери снимок, содержащий
саму местную приёмку, действовавшие `scope.md` и общее поручение. Проверка
сопоставляет мандат решения с записями этого снимка и сверяет роль, этап,
отрезок работы и существенные входы общего поручения. Этот снимок остаётся
основанием законного вклада после закрытия функции. Расширение мандата
действует на будущие решения. Прежняя местная приёмка без адреса
мандата читается, а для её передачи или применения установи историческое
основание или проведи новую приёмку в надлежащей роли.

Если `assignment.research_review: true`, перед приёмкой нужна последняя
запись этой попытки в `research_reviews`: `attempt`, `revision`, `by`,
`result` (Git-адрес проверенного отчёта), `source` (Git-адрес заключения),
`decisive_evidence` (решающие Git-адреса) и `open_required` (нерешённые
обязательные замечания). При пересмотре
сохрани в `revisions` прежние `revision` и `basis`, а также
`authorized_by`, `source` и `reason` изменения. Для восстановления прежней
даты `restored_from` ведёт к историческому `task.json` с тем же полным
номером, прежней редакцией, самим решением и его наблюдениями. При прежней
ссылке на отдельный JSON найди снимок своей карточки с решением и укажи его.
Если сохранилось лишь наблюдение либо отдельно записанное решение без
подтверждённой принадлежности, проверь результат для приёмки текущей датой.

**Зависимость.** Помимо задачи, обязательства и ID приёмки, для действия нужен
`basis` с адресом карточки, в которой сохранены выбранная приёмка и её
наблюдения. Проверь доступность адресов, на которые ссылаются выбранные
наблюдения и само решение. Для ссылки с коммитом проверяется файл в
этом коммите. Отозванная или заменённая приёмка требует нового основания.
Изменение проверенных входов и артефактов при прежнем обязательстве требует
перепроверки. Если редактор потребителя установил совместимость, он может
сохранить в связи `compatibility` с `by`, `reason` и `commit` проверенных
новых байтов. Решение о совместимости требует действующей приёмки и
доступности её свидетельств. Сверка проходит по зависимостям затронутой работы, включая
выдающий мандат. Папка, ожидающая переноса, остаётся доступна по полному номеру;
для действия требуется сохранённая актуальная приёмка.
При сверке существенного материала задачи программа ищет его по номеру
и имени файла отдельно в рабочей папке, индексе и последнем коммите.
При частичном сохранении карточка и отчёт могут иметь разные папки в одном
слое. Расхождение байтов указывает найденный путь и слой. Если в одном
слое есть два адреса материала, переход ждёт сверки этих адресов.

<a id="move-review"></a>
### Осмотр и перенос папки

`move --root . --profile ПРОФИЛЬ --task НОМЕР` выводит JSON осмотра. Рабочий
путь находится в `card_paths.worktree`. `card_paths.index` и `card_paths.head`
перечисляют фактические пути карточки в индексе и последнем коммите.
В `files` по каждому пути внутри комплекта указаны доступные версии.
У рабочих файлов есть режим, SHA-256 и идентификатор сырых байтов Git.
У сохранённых версий есть путь, режим и идентификатор объекта. Индекс
показывает также стадию. Папки, включая пустые, входят в рабочий состав.
Значения `phase` и `next_step` помогают [продолжить работу](procedures/recovery.md#card-resume).
Если в карточке есть `waiting`, осмотр отдельно возвращает этот блок с
причиной и следующим шагом по задаче. При выполненном возврате в `open`
фаза `git` показывает доступный шаг сохранения, включая старые пути
материалов после записи одной карточки. После сохранения возврата осмотр
указывает ожидание по задаче, если оно осталось.

Для команды с `--actor СЕССИЯ --review ФАЙЛ` в JSON осмотра заполни два поля.

- `owners` содержит владельца по каждому пути из `files`, кроме корня `.`.
  Одно имя подтверждает общего владельца всех показанных версий. Если
  владельцы различаются, перечисли известные версии, например
  `{"worktree":"Автор","index":"Редактор","head":"Владелец проекта"}`.
  Используй ровно присутствующие ключи. При неизвестном владельце остановись
  до записи и выясни происхождение.
- `links` перечисляет сверенные обязательные ссылки. Пустой список означает,
  что таких ссылок после осмотра не обнаружено. У каждой записи есть
  `document`, `target` и `owner`. Для файла внутри задачи используй
  `{"task":"P/T-008","path":"report.md"}`. Для другого живого файла
  подойдёт путь от корня. Историческая цель использует коммит и путь в нём.
  Для относительной ссылки добавь её значение в `relative`. Команда
  проверяет наличие указанного текста и путь цели после переименования.
  Для известной обязательной ссылки, которая ещё препятствует переносу,
  сохрани у владельца `next_step`. Редактор отвечает за полноту списка,
  смысл ссылки и её якорь внутри документа.

Перенос требует действующего редактора, свежего осмотра, обычных файлов и
каталогов на одном томе. Приёмка проходит проверки `handoff`, включая
сохранённый результат или проверенную версию. Отмена, отказ и замена
требуют выясненного исхода попыток, возврат из архива — отзыва или явного
повторного открытия. Команда использует переименование без замещения.
На системе или файловой системе без этой операции переход останавливается.
Запись в Git выполняет [его владелец](procedures/adapt.md#task-move-git).

<a id="task-addresses"></a>
### Поиск и адреса материалов

`tasks --root . --profile ПРОФИЛЬ [ПОЛНЫЙ_НОМЕР]` выводит JSON. Без номера
он перечисляет все области и все три папки с сортировкой по полному номеру.
Каждая строка списка — объект с `id`, `path`, `location`,
`expected_location` и `card`. По номеру возвращается такой же объект, при
длинном описании с дополнительным `description_text`. Поле `card.parent`
задаёт дерево на любой глубине, `card.dependencies` — отдельные ссылки
на поставщиков результата. Для будущего обзора Python-точка входа
`TaskReader.from_profile(root, profile)` из `tools/task_reader.py` даёт
`list_tasks()`, `find(full_id)`, `show(full_id)`, `read_material(address)`
и сообщения `infos`. Данные одного экземпляра относятся к одному обходу.
При изменениях профиля и для повторной проверки после обнаруженного конфликта
создавай новый экземпляр. Программный читатель сообщает ошибку через
`read_support.Problem`. В командах `tasks` и `read` ошибки идут в stderr,
для полей и ссылок код 1, для неподдерживаемых форматов и конструкций код 2.

- **Текущий материал:** `{"task":"P/T-008","path":"report.md"}`. Путь
  отсчитывается внутри найденной папки, какая бы из трёх папок ни содержала её.
  Вызов `read --root . --profile ПРОФИЛЬ --task P/T-008 --path report.md`.
- **Исторические байты:** `{"commit":"ПОЛНЫЙ_КОММИТ","path":"тогдашний/путь"}`.
  Вызов `read --root . --commit ПОЛНЫЙ_КОММИТ --path тогдашний/путь`.
  Берутся точные байты обычного файла из локальной истории Git. Текущее
  размещение, текущий профиль и наличие файла на диске здесь не требуются.
  Путь проверяется в дереве этого коммита. Каталоги, символические ссылки
  и компоненты `..` отклоняются. Используй полный хеш объекта типа commit.
- **Запись внутри старого JSON:** добавь `select` к историческому адресу
  или аргумент `--select '{"work":"task-1","kind":"criterion","key":"C-1","revision":2}'`.
  В составном источнике `work` выбирает единственную работу, `kind`
  и `key` — поручение, критерий, попытку, результат или приёмку
  (`assignment`, `criterion`, `attempt`, `result`, `acceptance`).
  Для критерия, попытки и приёмки `revision` — редакция поручения, для
  поручения и результата — редакция самой записи. Для результата внутри
  реестра нужен также `attempt` с ключом попытки. Для отдельного JSON с
  поручением или результатом укажи его собственные `kind`, `key` и
  `revision`, без `work` и `attempt`. Если старый реестр ссылается на
  отдельный файл через `path`, читатель берёт этот путь из той же исторической
  редакции. Ответ с `select` — выбранный JSON, обычный ответ — байты.

Прежнее `check --state` применяет договор конкретного файла состояния.
Для его сверок рабочего дерева, HEAD и индекса используются прежние адреса
реестров и сохранённые в выбранном слое указатели на отдельные файлы.
Для реестра, вручную перемещённого в обход этого договора, точную прежнюю
версию можно читать явным адресом `read --commit … --path … --select …`.
Новые карточки и явное историческое чтение сохраняют старые записи.
Сценарии показаны в `examples/task-cards.md` полной поставки.

<a id="task-migration"></a>
## Записи подготовки перехода

Маршрут начинается с [действующего входа](procedures/adapt.md#partial-and-migration).
Редактор сохраняет отдельный JSON сверки. Пути к проектным файлам
отсчитываются от его корня. Поля сверки перечислены ниже.

- `entry` содержит пути прочитанных входных инструкций, `profile` — путь
  действующего заполненного профиля, `editor` — ответственного за сверку.
  `source` задаёт `kind` (`state` или `partial`), `path` и
  `diagnostic` с рабочей папкой `cwd`, командой `command` и её охватом
  `scope`. Если в профиле есть строка выбора источника, программа сверяет
  её с файлом и распознаёт прежние имена форматов. При текстовой навигации
  агент устанавливает выбор по входу, профилю и вызову. Команда в JSON
  служит записью наблюдения. Её выполняет агент после разбора, а
  инвентаризация вызывает встроенный читающий модуль прежнего формата.
- `scopes` связывает `P` и каждую `F-…` с прежним `source`.
  Для каждой области укажи `continuation` со старым номером работы и
  `next_step`. Пустой области соответствует `continuation: null`.
  Если в старой форме есть роль без сессии, можно добавить
  `editor` с полями `role` и `session`, когда это известно.
- `works` содержит ключ на каждый прежний номер. В каждом сопоставлении
  укажи `new` (полный номер), `owner`, `meaning`, `next_step` и
  `grounds`. У каждого основания в `grounds` есть `basis`,
  `status` (`applicable`, `recheck` или `wait`), `reason` и
  `next_step`. Для открытого ограничения заполни обычный блок `waiting`
  карточки. Одноимённые местные номера допустимы в разных новых областях.
  Старый номер сравнивается по правилам его источника.
- В `history` работы именуй [исторические адреса](#task-addresses).
  В её `materials` укажи рабочие файлы для точной копии рядом с карточкой.
  Общий `materials` дополняет инвентарь значимых файлов и ограниченных папок.
  `links` перечисляет `document`, точный относительный `link` и
  прежний `work`. Помощник сверяет наличие прямой Markdown-ссылки и
  её локальной файловой цели. Редактор подтверждает охват, якоря и смысл ссылок.
- `exceptions` хранит `level` (`task` или `switch`), `target`
  (работа или область), `owner`, `reason` и `next_step`. У удерживаемой
  задачи сохрани ожидание в её карточке. Общему препятствию соответствует
  область или затронутая работа. Невыясненный исход попытки с правом записи,
  Git или внешней операции и конфликт индекса дают общее препятствие.

Для стороннего текстового списка редактор перечисляет `rows` и проверяет
их полноту. Для этого выпиши номера непосредственно из выбранного списка
и сверь их с подготовленными карточками. Сравнение `rows` с `works`
проверяет согласованность сопоставления. Если в обеих частях пропущена одна
строка, её выявляет перечень из исходного списка. Строке нужны `id`,
физический номер `line` с единицы, точный
текст `text`, статус `status`, его автор `by`, дата `date`,
название `title`, цель `goal` и `criteria` обычной формы. Поле
`dependencies`, если есть, указывает старый `work`, `criterion` и
ключ `acceptance` либо `null`. Помощник сравнивает каждую строку с
исходными байтами и проверяет уникальность. Произвольные колонки, владельцы,
права, значение статуса и смысл свидетельства устанавливает редактор.
Зависимость и критерий опираются на действующее правило или датированное
решение владельца. При неоднозначной формулировке сохрани вопрос как
остаток. Отметь, какое решение нужно для запланированной строки, у
которой пока нет действующего поручения.

При переносе подтверждённой приёмки добавь к работе `accept`.
`decision` и `evidence` — имена в `history`, а
`observed_at` и `decided_at` — фактические даты или время с поясом.
Для штатной прежней записи адреса выбирают точные JSON приёмки и результата.
Имя `dates` указывает на сохранённую запись дат с `work`,
`acceptance`, `observed_at` и `decided_at`. Эта запись нужна, потому что
старый договор мог хранить автора и редакцию без даты. Для сторонней
приёмки поддерживается сохранённое JSON-решение с `id`, `work`, `by`,
`role`, `observed_at`, `decided_at`, `criteria` (ключи), `fact` и
историческим адресом `evidence`. При ином виде свидетельства или
неустановленной дате сохраняй исходный материал и остаток для редактора.
По профилю, журналу решений и ссылкам установи, где принимающий сейчас
правит или отзывает решение. В стороннем `accept.current_decision`
укажи путь к действующему файлу этого JSON. Он включается в снимок и
проверку передачи. При расхождении с исторической приёмкой редактор
разбирает изменение или отзыв. Если решение живёт только в истории и
проверено отсутствие отдельного действующего файла, укажи `null`.
Для прежнего сопоставления без поля помощник учитывает обычный файл по
историческому пути, если тот существует в рабочей папке. Иные действующие
нормы об отзыве или применимости добавь в `materials`.

Подтверждённое действующее назначение старого полного формата на подготовку
только для чтения может дать `proposal` с новым `id` и прежним
`executor`. Для иных действий сохраняй факты попыток, полномочия и
ограничения в исходном разборе. Записи выдачи на копии начинают с пустого
списка. Общие лимиты, резервы, фактические расходы, права старых сессий,
подтверждённые внешние исходы и данные интеграции остаются в
`legacy-scope.json` и `legacy.json`. Выдачу на дальнейшие действия ведёт
действующий владелец по применимым правилам.

При переносе выбранного старого основания действия зависимость получает
`confirmation`. Поле `task` указывает работу, чей результат действительно
выбрали. `assignment`, `result`, `acceptance` и `criterion` — исторические
адреса с ключами. Они связывают прежнее поручение, точную редакцию
результата, его приёмку и критерий зависимой работы. `check` задаёт ключ
выбранной проверки. При наличии старого решения о совместимости сохраняется
его запись `compatibility` внутри `confirmation`.
Обычная проверка действия сверяет действующие приёмки, покрытие критерия
и существенные входы именно выбранной проверки. Изменение входа требует
повторить проверку или согласовать новое основание. Если принятое
подтверждение нельзя привязать к действующей записи, оставь ожидание.

<a id="migration-bindings"></a>
### Сохранённые снимки и итог сверки

В папке кандидата лежат профиль проверки, `preparation.json` со снимком,
таблицей и исключениями и каталог `tasks`. В каждой папке задачи
`legacy.json` хранит точную исходную запись и происхождение материалов.
У рабочих файлов, индекса и последнего коммита отдельные отметки.
Исторические адреса указывают на прежние коммиты. Снимок датируется
фактическим временем инвентаризации.

Для проверки действий нужно сохранить подготовленные снимки в собственной
копии по [правилам Git](procedures/adapt.md#git-inspection). Команда
`prepare` собирает файлы, а владелец Git сохраняет выбранные снимки.
После первого сохранения добавь в `--bindings` адреса прежнего поручения
в новой карточке. Допустимые ключи файла приведены ниже.

| Поле | Что сопоставить с полным коммитом на копии |
| --- | --- |
| `decisions` | Номер принятой карточки → снимок её поручения и входов |
| `mandates` | Номер области функции → снимок её общей карточки |
| `dependencies` | Номер принятой карточки → снимок после записи основания её решения |
| `proposals` | Номер карточки → снимок местного поручения после записи мандата и основания зависимости |

Владелец сохраняет каждый следующий слой после соответствующего
`prepare --bindings … --previous-bindings …`. Путь карточки вычисляется
по её полному номеру. Все эти коммиты относятся к подготовке копии.
Даты старых событий и адреса старого Git остаются в исходных ссылках.
Для первой записи адресов достаточно `--bindings`. Повтори последнюю
команду `prepare` с итоговыми адресами для проверки идентичности.

`verify` сравнивает старые входы на обеих сторонах, содержимое кандидата,
доступность истории и действия по карточкам. Приёмки проверяются как
`handoff`, предложения как `assign`. Итог `ready` имеет код 0.
Для `prepare`, `verify` и `switch` нужны физически отдельные, невложенные корни.
Нерешённые стадии индекса в папке кандидата удерживают эти команды до
разбора владельцем Git. В ответе указываются путь и конфликтующие стадии.
Итоги `blocked` и `stale` имеют код 1 и показывают причину и следующий
шаг. Неподдерживаемый источник даёт код 2. Структурный `check` кандидата
проверяет карточки и связи, а штатная команда прежнего профиля читает
прежний источник.

`switch` применяет свежую сверку и меняет выбор в заполненном профиле.
Поле `pause` в указателе — путь к [записи выдачи](procedures/adapt.md#switch-to-task-cards).
После выбора карточек `reviewed` подтверждает возобновление, когда
`actor` совпадает с действующей сессией редактора общей области в `scope.md`.
`stopped` относится к продолжению при старом источнике. Если решение
расходится с выбранным источником, обычная проверка профиля и повтор
переключения указывают общий следующий шаг для сверки.
Поле `prepared` после переключения содержит путь `profile` подготовки и
перечень точных коммитов `commits` сохранённых оснований. В этих коммитах
проверяется профиль подготовки, который выбирал тот же каталог. В рабочем
профиле, индексе и HEAD действует новый выбор. Проверки поручений и
существенных файлов используют сохранённые байты на прежних основаниях.
Реквизиты выбора относятся к профилю. Карточки и исторические адреса
перенесённых решений от смены выбора не переписываются.
