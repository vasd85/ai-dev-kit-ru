# Записи 0.1-p2

Это договор между агентом и `kit.py check`. Агент редактирует JSON; пользователь принимает продуктовые решения в чате. Программа только читает записи и Git. Она проверяет формальные связи. Агент устанавливает достаточность полномочий, полноту входов, правдивость фактов и смысл проверок. Прямое редактирование программа не блокирует.

<a id="record-versions"></a>
## Версии и начальные формы

Сначала установи режим по профилю. В штатном источнике прочитай `format_version` до остальных полей. `0.1-p2` расширяет учёт до нескольких работ и последовательных итераций. `0.1-p1` читается прежним ограниченным путём: одна задача, одна попытка, явные файлы. Диагностика p1 поддерживает одну задачу и одну попытку с явными файлами и прежним `implement-and-test`, без непустых зависимостей и лимитов. Остановленный пример сохраняет `paused/stopped` и возвращает код 2 на `task/status`: это не подтверждение остальных полей или поддержка восстановления. Старые свидетельства не переписывают. Для переноса учебных данных вручную сохраняют прежние попытки, превращают задачу в элемент `works`, заменяют `write_files` на `write_scope`, `authorized_action` на `stage`, добавляют явные `actions` и список приёмок. Старые коммиты p1 не становятся свидетельствами p2: перед новым результатом сохраняют поручение и проверяют входы уже в p2. Автоматического переноса нет. До переноса читай [порядок смены источника](procedures/adapt.md#partial-and-migration). [Основание совместимости](reference/decisions.md#record-history).

`templates/state.json` — чистое состояние без назначений. Учебные записи находятся в полной поставке. `templates/result.json` требует фактического заполнения. Номер поставки хранится в [VERSION](VERSION).

<a id="state-and-history"></a>
## Состояние, источники и история

Все перечисленные поля обязательны, кроме явно необязательных. Неизвестные поля/версии не игнорируются. Повтор JSON-ключа, идентификатора, строки в списке или действующего локального источника — ошибка. Идентификаторы состояния, решения, итерации, работы, поручения, критерия, попытки, результата, проверки, приёмки и ограничения уникальны во всех загруженных областях. Вид ссылки определяется полем. ID начинается латинской буквой, далее допустимы буквы, цифры, `.`, `_`, `-`. Имена ролей и сессий не являются ID записей.

Редакция — положительное целое число; `true` и `1.0` не заменяют `1`. Изменение смысла поручения повышает его редакцию. Исправление представленного результата повышает редакцию результата. Статус сам не меняет поручение. Состояние повышает `revision` после содержательного обновления, чтобы сводки могли установить прочитанную редакцию. Git хранит историю; программа не доказывает всю последовательность переходов.

`assignment` и `attempt.result` содержат либо сам объект, либо только `{"path":"относительный/файл.json"}`. Требование/результат хранится один раз. Локальный внешний JSON проверяется так же, как встроенный. Повтор одного файла как двух живых записей запрещён. Внешнее `{"url":"https://…"}` явно непроверено и даёт код 2 для обязательного источника. Необязательный `external_links` даёт информационные сообщения; URL не загружаются и не заменяют обязательное свидетельство.

Markdown хранит профиль, нормативные решения и пояснения; произвольный смысл Markdown программа не понимает. Развёрнутое поручение штатного машинного формата — внешний JSON. Markdown может его пояснять, но не дублировать живые требования/статусы. Подключение к чужому формату определяется в [процедуре применения](procedures/adapt.md); сопоставление статусов не меняет программный формат.

### Общее и местное состояния

Короткий путь описан в [рабочем порядке](procedures/workflow.md#short-path).

Таблица показывает поля состояния.

| Поле | Смысл |
| --- | --- |
| `format_version` | `0.1-p2` |
| `id`, `revision` | Уникальная область учёта и её редакция |
| `scope` | `product` у файла входа; `feature` у местного файла |
| `profile` | Путь к существующему Markdown-профилю продукта |
| `editor` | `role`, `session`, `status` (`active`/`stopped`): единственный редактор, текущая сессия логической роли, состояние сессии |
| `iterations` | Непустой список `id`, `goal`, `status`: `planned`, `active`, `integrated`, `released` |
| `works` | Принадлежащие области работы; список может быть пустым при подготовке |
| `continuation` | `owner`, `last_completed`, `unverified` (список), `next_step`: достаточная передача из файлов |
| `actions` | Необязательный список текущих действий; правила ниже |
| `parent` | Только местно: `work`, `assignment_revision`, `commit` — общее поручение функции и полный коммит принятого местной ролью содержания |
| `write_owner`, `git_owner` | Только общая область, необязательны/`null` без выделенного отрезка. Оба обозначают область: ID продукта либо активной работы-функции. Конкретный писатель и исполнитель изменяющих Git-операций определяются её единственной местной попыткой |
| `decisions` | Только общая область, необязательный список `id`, `revision`, `source` (нормативный файл) |
| `revision_review` | Необязательная точка общего пересмотра R3 |
| `forecast` | Необязательный прогноз; внутри обязателен `estimate`, необязательны `observed` (число/`null`), `unit`, `analysis` |
| `real_limits`, `usage_views`, `external_links` | Необязательные ограничения, ссылки на первичные расходы и URL |

У итерации `integrated`/`released` обязателен `integration`: приёмка работы вида `integration` в этой же области/итерации. `released` требует также `release` — сохранённый факт доставки. Правдивость факта проверяет агент. Местная приёмка функции не закрывает общую интеграцию.

Общий реестр хранит работу-функцию и `local_state`, а не копию её очереди. Сессия функции меняется только местно; общее поручение назначает логическую роль. При местном продолжении `parent` совпадает с нынешней редакцией и содержанием общего поручения. Различие только номера HEAD не мешает, если принятое содержание то же. Чтение устаревшей области помогает выяснить остаток, но не разрешает реализацию.

<a id="assignment-and-inputs"></a>
## Работа, поручение и входы

Работа содержит `id`, `kind` (`task`, `question`, `feature`, `integration`), `iteration` (местная итерация), `status`. У `candidate` есть только эти поля и непустая `idea`: идея ещё не назначение. Остальные состояния имеют `assignment`; необязательны `attempts`, `active_attempt`, `acceptances`, `current_acceptance`, `blocker`. Только функция имеет `local_state`, необязательные `view` и `closure`.

Поля поручения показаны ниже.

| Поле | Смысл |
| --- | --- |
| `id`, `revision`, `goal`, `boundaries` | Точная норма и границы результата |
| `inputs` | Непустой список файлов/папок существенных входов, в пределах [поддерживаемых путей](#paths-and-git) |
| `write_scope` | Разрешённые файлы/папки кода, тестов, сборок и общего ресурса, внутри `inputs`; для анализа допустим `[]` |
| `criteria` | Непустой список `id`, `expectation`: наблюдаемые критерии |
| `plan` | Непустой список действий подходящей глубины |
| `acceptor` | `editor.role` этой области; роли могут совмещаться |
| `stage` | `prepare` — чтение/подготовка; `implement` — реализация внутри выданной области |
| `authority` | `by`, `source`: происхождение разрешения, существующий нормативный файл |
| `dependencies` | Необязательные `work`, `acceptance`, `criterion`; `acceptance:null` допустима для будущей незапущенной работы |
| `decisions` | Необязательные `id`, `revision` общих решений |
| `mandate` | Только функция: `role`, `stages` (из `prepare`/`implement`), `interfaces`, `closing` — местные полномочия и условие закрытия |

Местные этапы не расширяют общее разрешение: при общем `stage:prepare` в `mandate.stages` допустим только `prepare`. Общий `implement` может разрешать местную подготовку и реализацию. Противоречивые поля отклоняются, а не трактуются как дополнительное разрешение.

Профиль, источник разрешения и выбранные общие решения входят в `inputs`. Файлы состояния туда не входят: содержание поручения проверяется отдельно от статусов. Полноту входов выбирает агент. Папка включает сохранённые файлы и новые неигнорируемые файлы, поэтому устаревший перечень не скрывает добавление внутри области. Секреты, новые игнорируемые данные и неизвестная внешняя среда не объявляются проверенными по Git. Внешние JSON-поручения сравниваются по сохранённому содержанию, а не только по номеру редакции.

<a id="attempts-and-actions"></a>
## Попытки, состояния и действия

Попытка содержит `id`, `assignment_revision`, `executor`, `phase`, `effects`. Фаза: `assigned`, `running`, `unknown`, `stopped`, `finished`. `effects` — непустой набор из `read`, `write`, `git`, `external`. `write` включает изменяющие общую папку тесты/генераторы. Применимые правила этапа и записи своей памяти определяет [мандат роли](procedures/roles.md#mandate-and-effects). Диагностика проверяет сочетание `prepare` с эффектами при назначении, исполнении, приёмке, передаче и выборе результата текущим основанием. Невыбранная история остаётся читаемой.

Для `stopped`/`finished` обязателен `termination:{by,fact}` с фактическим основанием; у остальных его нет. При `external` обязателен `external_outcome`: `unknown`, `confirmed`, `not-performed`. Неизвестный внешний исход выясняют до повторения действия.

Непрекращённая попытка принадлежит `active_attempt`. Для диагностики активны фазы `assigned`, `running`, `unknown`; программа считает активные попытки с `write` или `git` и проверяет, что их не больше одной и что область совпадает с `write_owner`. `git_owner`, если указан, совпадает с `write_owner`. Любая активная попытка с `git` требует `git_owner` своей области. Для передачи действуют [правило ресурсов](procedures/roles.md#shared-resources) и [фактическая остановка](procedures/recovery.md#resume). Программа проверяет запись факта, но не удостоверяет остановку процесса. Для новой попытки запиши новый ID, сохрани прежние попытки и результаты.

Таблица связывает статус поручения с заявленным действием.

| Статус | Смысл |
| --- | --- |
| `ready` | Текущая `assigned` попытка; обязателен `assign` |
| `in_progress` | Текущая `running` попытка; обязателен `execute` |
| `submitted` | `finished` попытка с результатом; обязателен `review`, кандидат ещё не принят |
| `accepted` | `current_acceptance` выбирает приёмку текущей попытки и того же содержания поручения; исторические входы не обязаны быть нынешними |
| `blocked`, `paused`, `cancelled`, `revise` | Обязателен `blocker:{reason,next_step}`; допустим только `inspect`. Непрекращённая старая попытка может удерживать ресурс |
| `candidate` | Намеченная идея; допустимо чтение |

Для общей попытки координации функции и местных попыток применяй [правила мандата](procedures/roles.md#mandate-and-effects). Требование эффекта общей попытки агент сверяет отдельно. После общей приёмки функции обязательна `closure:{knowledge,obligations,owner}`: знания, открытые обязательства и владелец сопровождения. Местные исполнители прекращены, назначения ресурса освобождены. Малое последующее исправление можно вести обычной задачей.

Действие относится к работе в своём источнике: `work`, `kind`. Пара работы и вида действия уникальна. У `inspect` других полей нет: это только чтение/разбор. Остальные действия обязательно содержат `bases`, даже если независимой задаче достаточно `[]`.

`assign`, `execute`, `review` соответствуют таблице статусов. `handoff` выбирает принятый результат как актуальное основание передачи. Заблокированную работу передают через `inspect`, `blocker` и конкретный шаг `continuation`, без выдуманной готовности писать. `spend` проверяет отдельную расходную операцию и сам не разрешает запуск кода/внешнего действия.

<a id="results-and-acceptance"></a>
## Результат и историческая приёмка

Результат может сохраняться у исторической `stopped` или `finished` попытки. Для текущего кандидата действует таблица попыток и статусов. `attempt.result` пишет исполнитель, встроенно либо во внешнем локальном JSON. Поля: `id`, `revision`, `assignment_id`, `assignment_revision`, `attempt_id`, `executor`, `summary`, `commit`, `artifacts`, `checks`, `unverified`, `limitations`, `next_step`. Списки `unverified`, `limitations` могут быть пустыми; `next_step` — строка. `commit` — полный существующий коммит с поручением, назначением попытки и входами. `artifacts` — непустой список предъявленных файлов/папок из входов, сохранённых в коммите.

Проверка содержит `id`, `covers`, `command`, `cwd`, `expected`, `observed`, `outcome` (`passed`/`failed`), `environment`. `cwd` — безопасный относительный путь к папке проверки; `.` допустима. Исторический каталог проверяется по дереву сохранённого коммита и не обязан существовать сейчас. У собственного текущего кандидата `review`/`handoff` каталог должен существовать и сейчас. Пустой неотслеживаемый каталог не подтверждается историей Git: используйте сохранённую рабочую папку и отдельно опишите внешнюю среду. `covers` — непустой список точных обязательств `work`, `assignment_revision`, `criterion`. Проверка может покрыть чужое обязательство, если оно действительно проверялось. Смысл покрытия оценивает принимающий. **Порог представления и приёмки.** У всех собственных обязательных критериев точного кандидата должны быть успешные, применимые свидетельства с точным покрытием. Непроверенный критерий, недоступное обязательное свидетельство и неуспех не проходят порог. Старый неуспех сохраняется в отдельной попытке. Команда из записи не исполняется диагностикой.

Приёмки находятся в `work.acceptances`. Поля: `id`, `result`, `result_revision`, `assignment_revision`, `by`, `evidence`, `unresolved`, `applicability`. `evidence` выбирает успешные проверки данного результата и покрывает его собственные критерии. `by` равен принимающему в сохранённом поручении. `current_acceptance` существует только при `accepted`, выбирает результат `active_attempt` и то же содержание нынешнего поручения. Поздний ответ не заменяет новую приёмку. Исторические приёмки остаются при новом назначении без `current_acceptance`.

Для истории поручение, назначение и наличие обычного файла `authority.source` проверяются по коммиту результата. Исторический источник разрешения не обязан существовать сейчас, если результат не выбран текущим основанием. Путь всё равно проходит проверку границ и ссылок; действующий профиль каждой области обязателен. Текущее действие требует нынешний источник своего разрешения. Для собственного кандидата `review`/`handoff` дополнительно сравниваются поручение в нынешнем файле, HEAD, индексе и свежесть входов. Исключение для свидетельства уже принятой зависимости см. в [основаниях](#dependencies).

<a id="dependencies"></a>
## Текущие основания зависимостей

Для каждой зависимости нужен ровно один объект `bases`: `work`, `acceptance`, `criterion`, `result`, `result_revision`, `check`. Приёмка относится к нужной зависимости, которая остаётся принятой на выбранной приёмке. Текущее подтверждение может принадлежать другой работе, но его выбранная успешная проверка явно покрывает нужное обязательство и принята. Содержание поручения обязательства в коммите нового подтверждения должно точно совпадать с поручением из исходной приёмки: совпадения ID и номера недостаточно. Поручение обязательства строго сравнивается с рабочей записью, HEAD и индексом. Собственное историческое поручение выбранного подтверждения сравнивается отдельно с каждой из этих трёх версий, если та сохраняет ту же пару `assignment.id` + `revision`: подмена содержания при прежней паре запрещена. Законное новое поручение работы-подтверждения не заменяет её прежний принятый результат и не обесценивает подтверждение неизменного обязательства на тех же входах. Новая рабочая редакция не скрывает подмену старой редакции в HEAD или индексе. Собственный текущий кандидат по-прежнему сверяется строго. Сравниваются нормативные поля, а не весь реестр; старые приёмки не переписываются. Исключение — только `review` собственного текущего кандидата: его проверка может заново подтвердить и обязательство принятой зависимости после своей правки. Сам кандидат проходит все проверки поручения/входов, но не обязан принять себя заранее. Для отдельной следующей работы непринятый кандидат основанием не служит. Пустой список не заменяет зависимость. Неизвестные работы, критерии, ссылки на несуществующую ненулевую приёмку и циклы запрещены. Будущая зависимость с `acceptance:null` сама не запрещает независимое действие, но не разрешает зависимое.

В R1 A принята по A1 в C1. B меняет общий код и в C2 проверяет также обязательство A. Следующая работа хранит зависимость от приёмки A, а подтверждение выбирает B1/C2. A1 остаётся историей C1 и не блокирует C2. Если старое разрешение A архивировано, новое B может подтвердить точное поручение A на собственных действующих входах/разрешении. Входы A не становятся входами B автоматически. Выбор самого A1, напротив, требует актуальности всех его входов, включая источник разрешения; совместимость не заменяет отсутствующий источник и не разрешает иной текст обязательства. Выбор одного A1 при изменённых значимых входах не проходит.

При смене результата подтверждения обязателен непустой `replacements`. Каждый элемент хранит прежние `result`, `revision`, `check`, `reason`, `by`; первый относится к исходной приёмке зависимости. Прежние источники и связь обязательства сохраняются. Обоснованность замены проверяет агент.

Для незатрагивающей обязательство правки допустимо `compatibility` в основании: `from_commit`, `to_commit`, `work`, `assignment_revision`, `criterion`, `differences`, `reason`, `by`. Пара коммитов точная; `differences` перечисляет ровно изменённые входы выбранного свидетельства, список непустой. Новая сторона совпадает с нынешними входами. Надпись «совместимо» не является доказательством. Программа проверяет привязку, агент — отсутствие влияния. Изменившееся поведение требует новой проверки.

<a id="paths-and-git"></a>
## Пути, Git и существенные входы

`--root` — канонический корень обычного локального Git-репозитория, без символической ссылки в нём/родителях. Пути нормализованы и относительны ему; запрещены `..`, `.git`, обратная косая черта, двоеточие, переводы строки/NUL. Ссылки запрещены во всех компонентах и внутри зарегистрированных папок. Данные не задают дополнительный корень. Каждый отдельный путь `inputs` должен существовать при проверке текущего действия, кроме `inspect`. Весь корень (`.`) запрещён во входах. Артефакт подтверждается в сохранённом коммите. Новый файл опиши в поручении и покрой существующей папкой входов. Его будущий путь может быть в `write_scope` внутри этой папки. Если такой области нет, сначала согласуй создание допустимой основы. Состояние исключено из списка существенных входов. Точка `.` допустима для `cwd` проверки. Это доверенная локальная папка без одновременной подмены путей; защита от враждебной гонки не заявлена.

Сначала сохраняют входы/поручение в Git, потом проверяют, затем записывают результат с номером существующего коммита. Коммит не ссылается на самого себя. Отчёт можно сохранить следующим коммитом. У выбранного текущего результата сравниваются набор входов, содержание и права исполнения в проверенном коммите, нынешнем HEAD, индексе и рабочем дереве. Новые неигнорируемые файлы внутри области обнаруживаются. Сравниваются исходные рабочие байты, а не вывод о чистоте после Git-преобразования. Например, Git может считать файл с преобразованными окончаниями строк чистым, а диагностика отклонит отличие. Для выяснения используй [безопасный осмотр](procedures/adapt.md#git-inspection). Обязательное неподтверждённое условие остаётся открытым до установления поддерживаемой редакции. Различие SHA после объединения само не является изменением поведения: одинаковые итоговые входы допускают прежнее свидетельство.

<a id="diagnostics"></a>
## Диагностика

Для штатного локального Git-репозитория нужны Python 3 и три поставляемых модуля рядом. Установка библиотек не требуется. Из канонического корня при типовом размещении:

```sh
GIT_OPTIONAL_LOCKS=0 python3 -B .ai-kit/tools/kit.py check --root "$PWD" --state docs/ai-work/state.json
```

Для клона используй `.ai-dev-kit/kit/tools/kit.py`. Из вложенной папки подставь фактический путь к программе и полный канонический корень. `--state` всегда от корня. Моменты проверки определяет [рабочий порядок](procedures/workflow.md#diagnostic-transitions). Для чужого режима действуют [проверки агента](procedures/adapt.md#partial-and-migration). Для особого основания изготовления или установки прочитай [условия снимков](procedures/adapt.md#install-check).

Чтение использует `GIT_OPTIONAL_LOCKS=0`, очищенное от внедрённых `GIT_*` окружение, отключённые глобальную/системную конфигурации, hooks, fsmonitor, сеть, lazy fetch и замены объектов. Конфигурация сначала разбирается отдельным Git без обнаружения репозитория: `--git-dir=/dev/null`, `--no-includes`, переданные байты. Запрещены действующие ключи `include.*`, `includeIf.*`, `extensions.*`, `worktree.*`, `core.worktree`, `remote.*.promisor`, `remote.*.partialCloneFilter`. Безвредные слова в значениях/комментариях не дают отказа. Gitfile, worktree, внешние объекты, alternates/grafts и служебные ссылки не поддерживаются. При поиске новых входов внешний `core.excludesFile` переопределяется `/dev/null`; используются локальные `.gitignore` и `.git/info/exclude`. Обработчики diff/textconv, фильтры и команды из данных не запускаются.

Коды: `0` — формальных противоречий в заявленных действиях не найдено; `1` — неверные данные/несогласованность/ошибка чтения; `2` — неподдерживаемая версия, конструкция или неверные аргументы команды. Сообщается первая проблема с адресом записи. Русский Unicode сохраняется; непечатаемые в текущем потоке символы экранируются. INFO сообщает об ограничениях или наблюдениях без отказа. При успехе `inspect` проверен только разбор. Успех не выдаёт полномочия, не подтверждает качество продукта, всю историю, остановку или соблюдение текстовых условий роли. Действующий специальный мандат и роль редактора агент сверяет по [правилам ролей](procedures/roles.md#mandate-and-effects). Код 1 или 2 для обязательного условия оставляет его непроверенным.

<a id="coordination-records"></a>
## Записи координации и общего пересмотра

Поля общего поручения функции, местного состояния и завершения определены в [поручении](#assignment-and-inputs), [состоянии](#state-and-history) и [попытках](#attempts-and-actions). Перед использованием мандата открой [правило ролей](procedures/roles.md#mandate-and-effects). Одного уровня местного состояния достаточно для поддерживаемого формата: вложенная функция не поддерживается. Если сохранена необязательная `view`, диагностируется её точная ссылка и прочитанная редакция. Для местного действия кроме `inspect` общая работа должна быть `ready` или `in_progress`. Диагностика сверяет принятую редакцию и содержание общего поручения из `parent.commit` с действующей записью, а существенные нормативные входы (общий профиль, источник разрешения и выбранные решения) — в `parent.commit`, нынешнем HEAD, индексе и рабочих файлах. Просроченная сводка даёт отказ общего состояния.

`revision_review` содержит `decision`, `revision`, `owner`, `pending`, `updated`, `independent_actions`. Сначала сохраняют новое решение и остаток, затем обновляют поручения. `pending` точно перечисляет непринятые работы, ещё ссылающиеся на старую редакцию; `updated` — уже согласованные непринятые работы. Исторические принятые поручения не переписываются ради нового решения. Ответственный — редактор общей области. `independent_actions` объясняет допустимые действия, но машинные разрешения остаются в `actions`.

Порядок продолжения — [пересмотр](procedures/recovery.md#reassess).

<a id="cost-records"></a>
## Записи прогноза и ограничений

Сопоставимые неотрицательные конечные числа прогноза могут дать INFO о превышении без отказа или смены статуса. Отсутствие или `null` наблюдения означает неизвестное. До расходного действия применяй [порядок работы с ограничениями](procedures/workflow.md#progress-and-cost).

`real_limits` хранится только в общей области. Каждое ограничение содержит `id`, `source:{by,path}`, `scope` (работы, включая внутренние работы выбранной функции), `unit`, `cap`, `remaining`, `usage`, `allocations`. Источник разрешения существует локально. Числа в одной указанной единице неотрицательны и конечны. Дробные JSON-числа, включая экспоненциальную запись, читаются непосредственно как точные десятичные значения, без промежуточного двоичного `float`; суммы и сравнения ограничений выполняются рациональной арифметикой. Это единая политика для `cap`, `remaining`, `usage.amount`, `allocations.amount` и `spend.amount`. Например, расход `9007199254740993.0` превышает предел `9007199254740992`; формы `0.2`, `0.20` и `2e-1` обозначают одну величину. Отрицательные, неконечные, булевы и строковые значения не являются допустимыми суммами. Целые редакции по-прежнему требуют целый JSON-тип: `true` и `1.0` не заменяют редакцию `1`. Предела 53-битной точности нет; действуют ресурсы локального Python, а не обещание обработки чисел произвольного размера. `usage` — первичные записи `attempt`, `amount` (число/`null`), каждая попытка один раз в данном ограничении. Известная сумма не превышает `cap`. Известный `remaining` равен `cap` минус сумма; при неизвестном расходе остаток не объявляют известным.

`allocations` содержит `work`, `amount`: это распределение остатка, а не новые расходы. Одна работа не резервируется повторно; общая сумма не превышает известный остаток. Закрытая функция освобождает и прямое распределение, и распределения её внутренних работ. Ненулевое оставшееся назначение даёт отказ; нулевое допустимо. Редактор явно удаляет/обнуляет резерв и только затем распределяет освобождённый остаток другой работе. Программа сама не правит записи. Первичные расходы и ссылки `usage_views` сохраняются; принятие внутренней задачи активной функции само по себе резерв не освобождает. `usage_views` содержит только `limit`, `attempts`: ссылки на первичные расходы без добавляемой суммы. Поэтому сводка не прибавляет расход второй раз. Это проверка подготовленных чисел, не интегратор денег или квоты.

Действие `spend` дополнительно требует `limit`, `amount`, известный обязательный остаток и достаточное назначение этой работе. Неизвестный остаток запрещает соответствующий расход, а не независимое чтение/работу без него. Настоящие запреты, включая запрет покупать новые средства, исполняет агент; технического финансового барьера нет. Покупки и исследовательский опыт этими записями не разрешаются.
