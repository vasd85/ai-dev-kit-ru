# Версии комплекта и записей

<a id="release-version"></a>
## Версия поставки

Храни единственный номер всего комплекта в [VERSION](VERSION) в формате `X.Y.Z`. Документы, шаблоны, программы и тесты входят в эту поставку; отдельные версии каждому файлу не назначай. Точную редакцию файла устанавливай по коммиту или контрольной сумме.

Пока первая цифра равна нулю, применяй следующие правила.

| Изменение | Пример |
| --- | --- |
| Совместимое исправление ошибки без новых возможностей | `0.2.0` → `0.2.1` |
| Новая возможность или существенное изменение процесса | `0.2.1` → `0.3.0` |
| Несовместимое изменение | `0.2.1` → `0.3.0`; явно опиши несовместимость и переход |

Считай совместимость по поддерживаемым командам и входам, форматам данных, настройкам проекта, полномочиям и продолжению назначенной работы. Необходимость переносить данные, заменять неподдерживаемый вход или менять действующие обязательства означает несовместимое изменение. Обычная проверка обновления и фиксация версии в профиле сами по себе несовместимостью не являются. Изменения инструкций оценивай по поведению, даже если код и JSON прежние.

Переходи на `1.0.0`, когда определены и практически проверены поддерживаемые способы подключения и работы и принято обязательство сохранять их совместимость. После этого увеличивай последнее число для совместимых исправлений, среднее — для новых совместимых возможностей, первое — для несовместимых изменений. При повышении старшего числа обнуляй следующие. Для смешанного выпуска выбирай наибольший требуемый уровень изменения. Основа схемы — [SemVer](https://semver.org/lang/ru/).

В описании каждого выпуска укажи новые возможности, исправления, совместимость, необходимые действия в проекте и пределы проверки. У серии `0.N.P` среднее число само по себе не различает совместимое расширение и несовместимую перестройку.

Публикуй одну неизменяемую редакцию под одним номером и Git-тегом `vX.Y.Z`. После публикации исправляй новым выпуском; прежний тег и историю не переписывай. До публикации фиксируй проверяемый кандидат хешами или коммитом. Состав поставки и совпадение опубликованной редакции проверяй по [процедуре](procedures/adapt.md#full-kit-check).

<a id="record-version"></a>
## Версия формата и редакция записи

Версия формата рабочих записей использует ту же схему `X.Y.Z`, но изменяется независимо от версии поставки при изменении договора данных. Поддерживаемые значения и правила перехода определяет [договор форматов](formats.md#record-versions). Смена версии кита сама по себе не требует переписывать состояние проекта или историю.

Поле `revision` — последовательный номер изменения конкретной записи; сохраняй его положительным целым числом по [договору редакций](formats.md#state-and-history). Не заменяй его номером поставки или строкой `X.Y.Z`.
